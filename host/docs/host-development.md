# 宿主开发总纲

> Host 回答一个问题:**由谁把 Eidolon 的各个零件装配成一个可运行的整体?**
> 答案不是内核(不认识具体节点)、不是编辑器(职责是定义项目)、不是运行时
> (它本身是被装配的零件)——而是 Host,组合根。

## 1. 核心命题

Host 是 Eidolon 生态的**组合根**:唯一知道全部零件、并把它们装配成可运行整体的系统层。

- **Kernel** 定义计算模型——世界可以怎样运行;
- **DSL** 定义节点语言——世界规则怎样书写;
- **Host** 定义装配——外部世界怎样进入计算模型。

装配指的是:节点注册、资产绑定、插件加载、运行驱动、I/O 接入。这些动作不属于
内核的计算模型,也不属于任何一个零件的职责——它们需要唯一的主人,这就是 Host。
类比:内核是库,Host 是进程——库不知道谁会用它,进程决定装哪些包、开哪些通道、
以什么节奏驱动它。

## 2. 为什么需要 Host(设计原理)

### 2.1 内核是库,不是应用

内核零第三方依赖、不认识任何具体节点——"节点一律按包概念组织,由宿主注册"
(内核重构计划总则)。库需要一个进程来"使用"它:注册节点包、装载图资产、
驱动运行循环。这个进程就是 Host。

### 2.2 内核显式排除的能力必须有归宿

内核的重构计划已经明确画出了三条边界,被排除的一方统称"宿主侧":

- 实时调度(start/pause/resume)——"宿主侧能力,不进内核核心,确定性不受影响"(B7);
- 并发——"保持单线程,并发留给宿主多实例";
- 真实资产系统——内核只含假 AssetSystem,真实实现是"再实现项"(规格已裁定,实现留给宿主)。

### 2.3 注入节奏的主人

内核是同步 epoch 语义——"宿主反复 run"。谁来 run、以什么节拍 run(宿主节拍
`tick:` tag 约定、注入序列的构造)——这是运行框架的问题,不是计算模型的问题。
内核定义"一个 epoch 如何传播",Host 定义"epoch 何时开始、由谁注入"。

### 2.4 编辑器临时扮演宿主是验证期的交叉

当前编辑器的"编辑器内嵌引擎"(实时自驱、暂停闸门、内置节点注册)在事实上
扮演着宿主。这是短期验证安排——编辑器即调试器,需要真实运行图才能调试。
但编辑器的最终定位是项目创作环境,不是运行框架;宿主能力最终要从编辑器中收回。

### 2.5 Runtime 旧"宿主层"定位的自指问题

早期文档把 Runtime 称为"内核的宿主层"。但 Runtime 依赖内核、解释器、格式层,
它自己就是被装配的零件——一个零件不能同时是装配者。装配职责上移给 Host,
Runtime 降格为 Host 装配的运行部件(其职责不变)。

## 3. 术语裁定:"宿主"三义

"宿主"一词在生态中出现过三种用法,裁定如下:

| 用法 | 出处 | 裁定 |
|------|------|------|
| 宿主层 = Runtime | 顶层早期文档("Runtime 是内核的宿主层") | **旧义,已被取代**。Runtime 是 Host 装配的运行部件,其职责(装载、驱动、I/O、生命周期)不变 |
| 宿主侧能力 | 内核文档(实时调度等"不进内核核心"的能力) | **保留**。这是 Host 职责清单的内容来源,不是另一个实体 |
| Host(组合根) | host/README | **本文档主体**。生态边界,尚未实现 |

## 4. Host 的职责边界

**Host 负责装配,全部职责都有既有裁定依据:**

| 职责 | 依据 | 说明 |
|------|------|------|
| 节点注册 | "节点由宿主注册" | 收集节点包的 NodeType 注册进内核,使图资产中的 type_name 可实例化;内核不内置任何具体节点 |
| 资产装配 | 真实 AssetSystem 是再实现项 | 按已裁定的资产协议(AssetIn/AssetRef/构建期解析/Capability 注入/Null 降级)把能力以 Capability 绑定到节点声明的资产槽位;"声明即必须"的构建期解析由宿主驱动 |
| 插件发现与加载 | "包概念" + 外部节点 ABI | 外部节点包、能力包的发现、加载与生命周期管理;每个可独立演化、独立发布的子项目对宿主而言就是一个插件 |
| 依赖解析与完整性验证(Resolve) | 节点实现三类来源模型(能力定位文档 §5) | 装载工程先做依赖解析:内核节点 / 脚本资产 / 内嵌插件 / 资源全部满足才进入实例化;解析失败是装载错误(Project Resolution Failure),不进内核执行 |
| DSL 承载 | DSL 语义冻结于内核仓 | 宿主承载"定义 → 编译 → 注册"的装配路径(脚本节点编译即此路径的实例);宿主不重新定义节点语言 |
| 运行驱动 | B7 实时调度 + 注入节奏 | 宿主节拍(`tick:` tag 约定)、start/pause/resume、生命周期管理 |
| 并发边界 | "并发留给宿主多实例" | 单图单线程语义不变,并发由宿主以多实例承担 |
| I/O 装配 | Runtime 提供 I/O 能力 | 把装配对象提供的 I/O 通道接入计算模型;I/O 的语义与表现由工程与 Presentation 定义,Host 不规定 |

**不属于 Host:** 执行语义与计算模型(内核)、节点语言的语义(DSL,冻结于内核仓)、
数据格式(协议层与资产类型层)、领域知识(能力库、资产类型层)、
I/O 的语义与表现(工程 + Presentation,编辑器五个编辑域的产物)。

## 5. 装配对象与宿主服务(定义)

### 5.1 三个装配对象

| 对象 | 定义 |
|------|------|
| **Editor** | 项目创作环境:使用者界面层(studio)整合图编辑服务(graph-editor),回答"这个项目是什么"。宿主把它装配进来,获得"定义项目"的能力。**与 Runtime 是同一系统的两种输出形态**(开发者 / 玩家,类比引擎编辑器视口与打包后的运行窗口),内部一致:共享内核、资产系统与工程装载路径 |
| **Runtime** | 运行形态:当前 Web 形态的运行入口(runtime 组合入口)。提供 I/O 能力,不规定 I/O 语义与表现;面对玩家,**页面展示是表现资产的一部分**(能力定位文档 §7)。宿主把它装配进来,获得"运行项目"的能力 |
| **Project** | 装配数据:图工程——由资产类型层的图工程模块定义的物理形态(目录工程 ↔ 标准包,双向无损互转;图资产 + 编辑器元数据 + 全局变量初值 + 资源)。宿主装载它,得到要运行的世界 |

### 5.2 Common Host Services(宿主自有层)

| 服务 | 定义 | 边界 |
|------|------|------|
| **Registry** | 节点注册表:收集全部 NodeType 注册进内核,使图资产中的 type_name 可实例化。内核不内置任何具体节点,"由宿主注册"的落点 | 只做收集与注册,不定义节点——节点是包;是运行时索引,**不记录依赖来源的事实**(来源由工程的依赖声明与内嵌插件记录) |
| **Assets** | 资产系统的**环境装配面**:按已裁定的资产协议注册资产种类(工厂)、提供凭证与创建参数、注入解析器,把能力(如 LLM 能力库)以 Capability 绑定到节点声明的 AssetIn 槽位 | 资产系统本体是**内核级基础设施**(未实现,内核重构"再实现项"),编辑器和运行时共享以保持内部一致——宿主不重复实现本体;使用面与管理面分离的语义不变 |
| **DSL** | 节点定义语言的宿主侧承载:"定义 → 编译 → 注册"的装配路径(脚本节点编译即此路径的实例) | DSL 语言本身的语义冻结于内核仓(编译目标 = NodeType 语义 IR);宿主不重新定义节点语言 |
| **Plugins** | 插件发现:回答"环境中有哪些可用的 Provider"(插件、能力包),并负责加载与生命周期 | 与 Registry 分离——**Plugins 管发现与加载,Registry 管 Provider → NodeType 的索引**;包内节点的语义归包自身;**暂不实现,只预留位置** |

装配链(启动过程):

```text
Plugin Discovery → Provider Loading → Registry → Asset Kinds(能力装配)→ Project Loading(Resolve)→ Kernel
```

内核只看到已注册的 NodeType 与 Graph,不知道 Plugin / Package / Project /
Provider 的任何概念,也不知道任何具体能力(只认 AssetIn / AssetRef /
Capability 协议)——这才是组合根。

## 6. 现状盘点:宿主能力的临时载体

短期验证允许交叉,当前宿主侧能力散落在验证期载体中。这是**现状事实**,不是最终形态:

| 宿主侧能力 | 当前载体 | 最终归宿 |
|-----------|---------|---------|
| 实时调度 / 暂停闸门 / 运行会话 | 编辑器内嵌引擎(World 自驱) | Host 运行驱动 |
| 宿主功能模块(RNG / 配置 / 控制台) | 内核仓的宿主功能包 | Host 公共设施 |
| 内置节点注册 | 编辑器服务(调色板数据源) | Host Registry |
| 能力接入(LLM 等) | 无——编辑器不实现 LLM 封装,能力库待装配 | Host Assets |

**裁定**:验证期允许交叉,载体照旧服务于验证;**Host 是最终层次**。Host 启动时
以装配面重新设计,不以任一载体为蓝本——编辑器的内嵌引擎服务于"编辑器即调试器",
与组合根的形态不是同一件事。

## 7. 启动条件与开发阶段

**启动条件 = 内核稳定**:大内核重构计划阶段 B 完成——"在冻结基准语义上实现全部
保留功能,编辑/运行时共用同一内核,与冻结基准无语义漂移"。在此之前 Host 只做
文档,不写代码(本总纲即文档阶段的产出;内核阶段 B 暴露的宿主侧需求在此登记)。

**当前冻结的是职责地图而非实现**(职责地图文档 §4):依赖方向、所有权、
生命周期与"允许知道什么"先行;页面系统、插件系统、资产系统 API 均不实现。

**阶段表(草案,随内核阶段 B 结果调整;每阶段遵循"先最小闭环验证契约形状,再扩大范围"):**

| 阶段 | 目标 | 验证点 |
|------|------|--------|
| H0(当前) | 文档规定与定义补齐;观察内核阶段 B 暴露的宿主侧需求(B7 实时调度是第一份) | 本总纲被采纳;宿主侧需求有登记处 |
| H1 Registry 最小闭环 | Host 进程装载内核 + 注册节点包 + 驱动一张图 | 不经编辑器即可注册与运行;"由宿主注册"从编辑器手中收回 |
| H2 Assets 环境装配面 | 资产种类注册 + 能力绑定(LLM 能力库首批);资产系统本体属内核级再实现项 | 声明 AssetIn 的节点在宿主装配下获得真实能力并执行 |
| H3 Plugins 边界(暂缓,只留位置) | 外部节点包 / 能力包的发现与加载 | 插件系统成熟前不实现;职责与边界已预留 |
| H4 组合装配对象 | Editor / Runtime 以依赖形式接入;Project 装载路径(Resolve 两阶段:依赖解析 → 实例化;目录工程 / 标准包 → 图实例) | 编辑器编辑的工程 = Host 运行的世界,同一内核、同一图资产 |
| H5 并发多实例 | 宿主多实例承担并发 | 单图确定性不变;多实例隔离契约成立 |

## 8. 开发约束

1. **新声明体系五问**。Plugins 发现协议等任何新的声明体系,从第一天起同时设计
   语义模型与表达语言两个维度,先过五问:① 运行语义是什么?② 稳定 IR 是什么?
   ③ 合法表达语言是什么?④ 哪些非法状态由语言直接消除?⑤ 哪些问题必须留给运行时?
2. **测试策略**。装配契约(注册 → 构建 → 运行闭环)属"稳定接口"层,按契约级
   测试;宿主内部实现属"实现细节"层,职责边界入文档前不补测(顶层测试策略文档)。
3. **文档规范**。边界优先、不做临时方案、只呈现决策、权威来源唯一——本总纲是
   Host 的权威来源,host/README 是摘要(顶层文档编写规范)。
4. **环境与依赖**。Host 是应用 / 服务类项目(独立 venv,重依赖汇聚点之一);
   进入 rev 传播依赖图后,传播链扩展为工程事项,不在本总纲裁定。
