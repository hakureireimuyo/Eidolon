# 核心架构哲学与项目定位

> 本文档记录 Eidolon 设计对话中**最终确定**的全局架构理念（已剔除被推翻的方案与过渡讨论）。这些理念约束后续 eidolon-runtime / eidolon-mind / eidolon-world 等未来层的方向。
> 相关文档：[数据容器与项目工程层](./data-container-project-layer.md) · [运行时核心设计](./runtime-core-design.md) · [独立项目职责与能力边界](./project-responsibilities.md)

## 1. 项目本质的重定义

Eidolon 不再只是"AI 角色聊天系统"，而是一个**可演化的叙事 / 模拟运行时（Narrative / Simulation Runtime）**，更接近"叙事游戏引擎"。

- LLM 只是其中负责**自然语言生成与局部推理**的组件，不负责决定剧情走向或世界演化。
- 剧情不再是一棵固定树，而是一个动态运行的世界（详见 [剧情 / 世界 / 叙事引擎](./narrative-world-engine.md)）。

## 2. 三件同构的事

| 层 | 解决的问题 | 核心原则 |
|----|-----------|---------|
| 数据容器（协议层） | 未知的数据如何存在 | 协议无知，未知数据静默保留 |
| 运行时 | 未知的能力如何参与运行 | 内核领域无知，未知扩展可参与状态演化 |
| Agent / 扩展 | 解释数据、推动状态演化 | 各 Agent 是状态转换器 |

三者应具有相似的"允许未知生长"的哲学：数据容器不拒绝不理解的模块；运行时也不应拒绝尚未实现的扩展（见 [运行时核心设计](./runtime-core-design.md)）。

## 3. 状态 / 能力 / 模型 完全解耦

- **状态**由系统维护（机器可计算）。
- **能力（Agent / Processor）**是状态转换器，读取所需状态、写入负责区域。
- **模型**是可替换的执行节点（LLM / 图片模型 / 视频模型 / 规则引擎）。

系统决定"发生什么"，LLM 负责"描述发生过程"——类比：物理引擎决定物体运动，渲染引擎负责显示。因此**LLM 是表现层 / 语言接口，不是大脑**。

## 4. "从零实现"的决策

不复用 SillyTavern 等聊天框架作为内核。

- 被排除原因：其核心抽象是"请求—响应的一次对话"；而本系统是"持续运行、维护内部状态、按环境变化采取行动的状态系统"，二者时间模型根本不同。
- SillyTavern（及同类）至多作为**外围兼容层**：角色卡输入格式参考、模型 API 适配经验、聊天 UI 借鉴。它不应成为基础设施。

## 5. 抽象层级的提升

从 `Character Runtime` 提升为 `Simulation Runtime`——**角色只是世界中的一种实体**，人格 / 世界 / 经济 / 记忆都是不同类型的状态容器。

这意味着后续 Git 仓库结构、模块划分、数据格式设计，都应按"**引擎项目**"而非"应用项目"来设计。

## 6. 思考时可借用的范式（非照搬）

- 游戏引擎的 ECS（Entity Component System）
- 操作系统的事件循环 / 进程调度
- 分布式系统的消息总线
- 数据库的事件溯源（Event Sourcing）
- Agent 框架的任务调度
