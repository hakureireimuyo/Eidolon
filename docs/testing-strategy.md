# 测试策略(架构演化期)

> 本文档规定 Eidolon 生态在**架构演化期**的测试编写原则:什么值得测、什么暂不测、现有测试如何处理。适用于所有子项目。
> 原则来源:[项目职责与能力边界](./project-responsibilities.md) 的"稳定进核心,不稳定成扩展"。测试遵循同一原则——**隔离变化,而不是阻止变化**。

## 1. 核心命题

> **测试保护稳定事实,不保护当前实现。**

项目当前处于架构快速演化期:

- **已经稳定**:协议层(容器格式已冻结)、资产类型层的数据格式
- **仍在成形**:运行时组合入口的调度方式、Context Compiler 的内部过程、运行时解释器的内部步骤
- **尚未启动**:未来层(世界系统、人格系统)的领域规则与实现

这一阶段的目标不是覆盖率,而是:**以较低维护成本保护较高价值的系统契约。** 一份绑定在"当前实现"上的测试,会在下一次重构中变成重构成本本身。

## 2. 唯一判据

编写任何测试之前,先回答:

> **如果明天把这个模块完全重写,这个测试表达的契约还应该成立吗?**

| 回答 | 处理 |
|------|------|
| 成立 | 写。它保护的是契约,不是实现 |
| 不确定(模块职责边界尚未确定) | 不写,等边界确定后补 |
| 不成立(只是在验证当前内部调用顺序) | 不写;已存在的此类测试在重构时删除 |

## 3. 测什么:结果、不变量与实现细节

### 3.1 测结果,不测过程

系统对外提供的语义是结果:"给定事件与状态,产生确定的状态变化"。

```python
# ✅ 断言结果——事件推进后,世界状态产生确定变化(示意,非真实 API)
assert 世界状态.门 == "打开"
```

```python
# ❌ 断言过程——内部函数被按某种顺序调用
mock.条件判断.assert_called_three_times()
mock.事件分发.assert_called_once()
```

过程随实现变化,结果是系统真正的对外语义。架构演化期,测试应明显偏向结果。

### 3.2 测不变量,不测拼装细节

不变量是"整个模块重写后仍然希望成立"的架构事实:

- 数据容器只提供初始数据,不承载运行时状态
- 世界状态由运行时管理,模型输出不能直接决定状态——必须经过解析与规则约束
- 数据块 → 内存对象的解释发生在运行时解释器中,组合入口只按类型标签路由

值得测的是这些边界是否成立;不值得测的是某个具体 prompt 模板拼出的某个具体字符串。

## 4. 三层测试密度

按稳定性把测试对象分为三层,密度递减:

| 层级 | 内容 | 密度 | 说明 |
|------|------|:----:|------|
| 稳定事实 | 已冻结的协议行为、已确定的数据格式、领域状态转换规则、复杂算法 | 高 | 协议层已冻结,其测试是当前最有价值的资产——上层任何重构都应继续成立 |
| 稳定接口 | 已形成稳定概念的公共接口(容器视图、解释器的输入输出契约) | 中 | 只测契约级行为,不逐一覆盖内部方法 |
| 实现细节 | 调度顺序、Context Compiler 内部步骤、prompt 拼装、临时实现 | 低到零 | 职责边界确定后再补;宁可暂时没有测试 |

推论:

- **测试代码多于生产代码本身不是问题**——解析与校验类代码天然需要大量边界用例。需要警惕的是测试的**耦合方向**:若测试绑定内部调用关系、每次重构都要重写,说明它放错了层级。
- **运行时解释器处于两层之间**:其输入输出契约(数据块 → 类型化内存对象)已稳定,按第二层测;其内部实现步骤仍可能演化,按第三层处理。
- 覆盖率数字在这一阶段没有意义,不设定任何覆盖率目标。

## 5. 现有测试的处理

- **保持不动**。现有测试冻结为当前行为的快照,不再扩充、不追求补全。
- **允许失效**。架构纠正导致旧测试失效时,改测试,不改架构——测试不是架构的主人。若为了测试通过而维持一个已认定错误的架构,说明测试在反噬设计。
- 重构时,把失效测试逐个过一遍第 2 节的判据:契约仍应成立 → 更新测试;只验证旧实现 → 删除。

## 6. 补测时机

以下任一条件成立,对应模块才解锁补测(并按第 2 节判据执行):

1. **职责边界确定**——模块的职责与边界已写入设计文档
2. **领域规则确认**——例如"信任超过阈值解锁隐藏路线"这类世界规则被正式确定
3. **数据格式定稿**——某种资产类型的格式冻结

未来层(世界系统、人格系统)启动后,其**领域规则与数据格式**属于第一层(高密度);其内部实现仍属第三层。

## 7. 检查清单

新增或修改测试前,逐条自检:

1. [ ] 用"完全重写"判据问过自己了吗?答案是什么?
2. [ ] 断言的是结果/状态,还是内部调用序列?
3. [ ] 被测概念在文档中有稳定定义吗?(职责边界未入文档 = 未稳定)
4. [ ] 这个测试会因调度顺序、prompt 模板、内部步骤调整而失效吗?会 → 暂不写
5. [ ] 有没有为了保住旧测试而放弃更正确的架构?有 → 改测试
6. [ ] 测试保护的是已冻结的契约(协议行为、数据格式)吗?是 → 这是最有价值的测试
