# 能力定位:资产关系、项目打包与节点扩展的实现层分配

> 本文档回答一个问题:**一项跨层能力(资产关系系统 / 项目打包 / 节点扩展 /
> 存档打包)由哪一层实现**——语义、格式、实现、装配、界面各落在谁手里。
> 总原则:语义与协议归内核(以冻结裁定为准),数据格式归协议层与资产类型层,
> 能力实现归能力库与独立包,装配归 Host,界面与触发归编辑器层;拆分线沿
> 已冻结的协议面走(类型标签路由 / NodeType 语义 IR / AssetRef-Capability 协议)。
> 相关文档:[职责地图:正交维度与依赖轴](./responsibility-map.md) · [项目职责与能力边界](./project-responsibilities.md) · [宿主开发总纲](../host/docs/host-development.md) ·
> 内核 [Asset 模型](../kernel/eidolon_graph_ref/docs/graph-assets.md) · [资产协议](../kernel/eidolon_graph_ref/docs/graph-asset-protocols.md) ·
> [图工程格式规范](../asset-types/eidolon-graph-project/docs/graph-project-format.md)

## 1. 判定方法(五条)

| # | 维度 | 落点 | 说明 |
|---|------|------|------|
| 1 | 语义 / 协议(什么关系合法、错误如何分层) | 内核 | 以冻结裁定为准;内核未裁定的先裁定再实现 |
| 2 | 数据格式(如何序列化、版本化) | 协议层(容器)+ 资产类型层(条目) | 协议无知,条目有知 |
| 3 | 能力实现(能力本身怎么做) | 能力库 / 独立包 | 零图概念,可脱离节点测试 |
| 4 | 装配(实例化、注册、绑定、生命周期、环境配置) | Host | 外部世界进入计算模型的动作 |
| 5 | 界面与触发(用户何时做) | 编辑器层 | 消费底层能力,不重实现 |

## 2. 资产关系系统

### 2.1 两个平面,不混淆

"资产"在生态中有两个平面,定位裁定不同:

| 平面 | 内容 | 关系形态 | 裁定状态 |
|------|------|---------|---------|
| 资源平面(数据资产) | 字节 + 语义声明 + ID 关联(resources/、条目) | 存储归协议层,语义归资产类型层,资源 ID 关联 | 已裁定(资源管理文档),无新裁定 |
| 能力平面(运行时资产) | Asset / AssetRef / Capability / AssetIn | 本节的"资产关系系统" | 语义已冻结,真实实现未落地 |

### 2.2 能力平面的实现层分配

| 环节 | 层 | 依据 |
|------|-----|------|
| 关系语义(声明即必须、构建期解析、错误分层、使用面/管理面分离、降级经 Null 资产) | **内核**(已冻结) | graph-assets.md + graph-asset-protocols.md,假 AssetSystem 验证通过 |
| 关系声明(节点需要什么 = AssetIn;图用哪个 = AssetRef/binding) | DSL 注解 + 图定义,序列化进图资产 | "需要什么→使用哪个→实际是什么"三层分属声明/图/实例 |
| 能力实现(Capability 提供方 + 管理面) | **能力库 / 资产实现包** | 资产协议 §16-17:资产可脱离节点独立测试、可替换 |
| 使用协议(Capability Protocol) | 随资产实现包发布 | 节点包生态的稳定边界,与节点协议 ABI 同地位 |
| 实例管理(工厂、创建参数、共享策略、健康、恢复、销毁)= 真实 Asset Management System | **资产系统本体 = 内核级基础设施**(未实现,内核重构"再实现项",规格已冻结)+ **Host** 提供环境装配面 | asset-protocols §9.1;创建参数属运行环境,不得泄漏进图(§12) |

**裁定(2026-08-23 补充修正):真实资产系统本体是内核级基础设施,不是 Host
独有能力。** 资产系统尚未实现,是内核重构的"再实现项"(规格已冻结);它作为
稳定核心被编辑器和运行时共同依赖——**是两者内部一致的基础**,并深度参与
数据、引用与图运行时的物理存储(其范围是否跨越资源平面与能力平面,留待
裁定)。Host 的 Assets 服务是它的**环境装配面**:注册资产种类(工厂)、提供
凭证与创建参数、注入解析器——本体归内核级,环境归 Host。图定义永远只含
AssetRef,不含任何环境配置。

能力库的依赖方向同时裁定:**能力是被依赖的底层**(零图概念、零内核协议
依赖);依赖它的是 Host 与节点/资产实现包,内核不知道任何具体能力——
"封装为节点"的精确形态是节点声明 AssetIn + 能力实现作为资产注入(内核
B4 按此重写),不是旧"节点封装层"形态。

## 3. 项目打包

| 环节 | 层 | 依据 |
|------|-----|------|
| 打包能力(目录工程 ↔ 标准包双向无损互转) | **资产类型层**(图工程模块) | 组装是唯一同时感知协议层与资产类型层的环节(资源管理文档写入路径);图工程格式规范已裁定已实现 |
| 打包触发(导出 / 分发) | **编辑器层** | 编辑器消费底层能力,不重实现;图编辑器路线已含打包为分发形态 |
| 内容校验 | 项目层浅校验 + 内核深校验 | 图工程格式规范 §6:项目层不解析图语义 |
| 装载(工程 → 图实例) | **Host**(Project 装载路径) | 宿主开发总纲 §5.1:Host 只装载,不打包 |
| 角色卡打包(.cart/.png) | 同理:资产类型层组装 + 编辑器(studio)触发 | 已实现,同一模式 |

**裁定:Host 不实现打包。** 打包能力是格式定义的一部分(双向无损互转属于
图工程格式规范),归资产类型层;Host 的职责止于装载。这一条防止 Host 膨胀为
"万能工具层"——装配者不做格式,格式者不做运行。

**工程包 = 完整可移植运行单元**:不是 Graph + Assets 的简单组合——至少逻辑上
包含工程定义、图、资产、节点依赖声明、脚本实现与内嵌插件(§5.6)。打包能力
仍归资产类型层,打包内容的边界由 §5 的依赖模型决定。

## 4. 节点扩展

| 环节 | 层 | 说明 |
|------|-----|------|
| 节点语言(定义如何书写) | **内核仓**,语义冻结 | 编译目标 = NodeType 语义 IR;内核核心包不感知 DSL |
| 节点定义(NodeDefinition 实现) | **节点包**(独立仓库) | 内置节点包现居内核仓 = 验证期交叉,最终按包概念独立 |
| 编译(DSL → NodeType) | DSL 编译链 | 语言归内核仓;承载(谁来跑编译)归 Host 的 DSL 服务 |
| 注册(types 注册进内核) | **Host Registry** | "节点由宿主注册";内核不内置任何具体节点 |
| 发现 / 加载(外部节点包) | **Host Plugins** | 包概念与外部节点 ABI 的装配面 |
| 依赖描述与分发(工程需要哪些类型、实现从哪来) | **工程格式**(Node Requirement)+ 编辑器 | 三类来源模型,见 §5 |

**裁定:"节点扩展"不是某一层的能力。** 表达语言归内核,实例(包)归包作者,
进入运行环境归 Host(注册 + 发现),资产化归编辑器。这条链上的每一环都沿
已冻结的协议面(NodeType IR / 外部节点 ABI)连接,各层互不感知内部实现。

## 5. 裁定:节点实现的三类来源(工程依赖模型)

> 2026-08-23 拍板。Eidolon 的工程依赖不是单一的"外部包依赖",而是三种
> 不同来源、不同分发责任的节点实现,不能用统一的 provider 概念抹平。

### 5.1 核心原则

> **Project 是自描述的,但不是自执行的;Node Provider 是可执行的,但不拥有
> Project;Host 负责把二者解析、验证并装配到 Kernel。**

### 5.2 三类实现来源

| 来源 | 实现所在 | 工程记录 | 完整性验证 |
|------|---------|---------|-----------|
| **内核节点** | 随 Eidolon 版本发布 | 只声明使用的 NodeType(对宿主环境的硬依赖) | Host 验证当前内核提供的 NodeType 完整匹配,缺一即不可执行——明确报错,不产生 Unknown Node、不允许忽略 |
| **脚本节点** | 工程内的脚本资产 | 节点引用脚本资产 | Host 验证被引用的脚本资产存在且可加载 |
| **插件节点** | 插件(内嵌进工程,或由环境提供) | 插件身份 + 版本 + 分发形态(内嵌 / 外部) | 内嵌:随工程加载;外部:环境必须已提供 |

对称关系:**内核节点 → NodeType 必须存在于内核;脚本节点 → 脚本资产必须
存在于工程**。二者都是工程完整性的必要条件,验证来源不同。

**脚本节点是一种实现机制,不是特殊 NodeType**——NodeType 一律遵循统一的
节点协议;Host / Script Runtime 负责把脚本资产装配成对应执行实现。

内核节点构成 Project → Eidolon 版本 / 内核能力集的依赖关系。

### 5.3 三级扩展机制

| 级别 | 载体 | 适合 | 分发 |
|------|------|------|------|
| 内核节点 | 内置实现 | 稳定、基础、跨项目复用 | 跟随 Eidolon 版本 |
| 脚本节点 | 脚本资产 | 工程私有快速扩展 | 随工程走 |
| 插件节点 | 插件束 | 成熟扩展,多工程复用 | 独立分发,可选择内嵌 |

**不是所有自定义行为都必须升级成插件。**

### 5.4 Node Requirement

工程记录的不是裸 type_name 字符串,而是结构化需求(逻辑形态,格式待
§5.8 ④⑤ 裁定):

```
Node Requirement
├── NodeType Identity
├── NodeType Version / Compatibility
└── Implementation Source
      ├── Kernel
      ├── Script Asset
      ├── Embedded Plugin
      └── External Plugin(未来扩展点)
```

- 内嵌与否**不改变插件身份与版本**:`com.example.weather@2.3.1, embedded`
  仍是有身份的插件,不是"一堆压缩进工程的代码";
- Provider 一对多:一个插件可提供多个 NodeType 与 Capability,工程依赖按
  **Provider → NodeType → Version / Compatibility** 三层描述,不假定
  "一个 NodeType = 一个 Python 包";
- 同一插件的内嵌 / 外部只是分发形态,Plugin Identity 保持不变。

### 5.5 工程完整性模型与两阶段装载

```
Executable(Project, Host)
  = KernelRequirementsSatisfied
  ∧ ScriptRequirementsSatisfied
  ∧ PluginRequirementsSatisfied
  ∧ AssetRequirementsSatisfied
```

Host 装载分两个阶段,"缺少依赖"与"运行时构建失败"不混在一起:

- **Resolve(依赖解析)**:读取依赖声明 → 检查内核节点 → 检查脚本资产 →
  加载内嵌插件 → 检查插件节点;任一不满足 = Project Resolution Failure
  (如 `Required NodeType foo.bar is not provided by current Kernel` /
  `Script Asset scripts/weather.py is missing`),**不进 Kernel**;
- **Instantiate(实例化)**:Resolved Project → 图构建 → 节点实例 → 内核执行。

Host 的核心职责之一,就是把这些外部世界的问题在进入内核之前消化掉。

### 5.6 工程的边界:可携带一切,除内核

```
Project Package(完整可移植运行单元)
├── Project Definition
├── Graphs
├── Assets                     ← 资源携带(数据依赖)
├── Node Requirements          ← 依赖声明
├── Script Implementations     ← 实现携带(代码资产)
└── Embedded Plugins           ← 实现携带(扩展单元)
```

工程携带它与生俱来拥有的一切,但**不能携带 Kernel**——否则工程就不再是
Eidolon 工程,而是完整的 Runtime 发行版。"资源携带"(普通 Asset)与
"实现携带"(Script / Embedded Plugin)必须分开考虑,这条边界直接决定
协议层、图工程格式、插件束与 Host 装载器四者之间的切分。

**容器统一性(2026-08-23 补充)**:工程包内的一切——图、资产、脚本、内嵌
插件、元数据——物理上都是协议层容器中的数据块(类型标签 + 注册的解析
程序),与任何资产同构。容器不在乎数据的形式:只要有实现、有声明注册,
即可打包进磁盘,由反向解析程序还原。插件以"内嵌数据"而非"安装的包"
进入工程,正是这条原则的产物。

### 5.7 节点扩展:一条跨层链

"节点扩展"不是一个层,**Host 拥有的是扩展系统的装配职责,不是扩展本身**:

| 环节 | 层 |
|------|-----|
| NodeType 语义 | 内核 / DSL |
| NodeType 实现 | 内核(内置)/ 脚本资产 / 插件 |
| 依赖描述与分发格式 | 工程格式(Project Format) |
| 发现、加载、注册、解析、验证 | Host |
| Node 实例 | 图工程(Graph) |
| 节点编辑界面 | 编辑器 |
| 节点执行 | 内核 |

### 5.8 下一步设计顺序

按依赖顺序推进,避免陷入局部格式问题:

```text
① NodeType Identity → ② Provider Identity → ③ Version / Compatibility
→ ④ Project Dependency Manifest → ⑤ NodeType Snapshot 是否进入工程
→ ⑥ Host Resolution → ⑦ Missing / Conflict / Incompatible 处理
→ ⑧ 插件分发机制
```

其中 ①–③ 是协议问题,④–⑤ 是工程格式问题,⑥–⑦ 是 Host 问题,⑧ 是插件
分发机制。两点既有倾向:

- ⑤ **倾向:允许携带 NodeType 的声明快照,不允许携带其实现**——快照是
  工程的自描述数据(依赖检查、静态验证、兼容判断、编辑器展示、迁移诊断),
  不是执行性依赖;最终执行仍须验证到真实的 Provider 实现;
- ② Provider Identity 描述的是 **Eidolon 依赖身份,不是 Python 包身份**——
  未来 Provider 可能是 Python / Rust / Native / Remote / WASM,工程协议
  不得被当前实现技术锁死。

## 6. 存档打包(裁定建议,待拍板)

- **快照语义:内核已冻结**(graph-assets.md §7)——只含 Graph 引用 + Node
  State + 执行状态 + AssetRef;恢复 = 恢复逻辑状态 + 对**当前**资产系统
  重新解析,绝不恢复旧资产对象。
- **建议定位**:存档条目格式归**资产类型层**(图工程新条目,条目级版本与
  损坏处理同 graph/editor_state 模式);打包容器复用**协议层**;何时保存 /
  恢复(生命周期触发)归 **Host**;编辑器可提供存档界面(可选)。
- **为什么 Host 不定义存档格式**:Host 只装配不定义格式(宿主开发总纲 §4);
  存档是"世界的可传输状态",与图工程同属资产类型层的格式职责。

## 7. 表现层(Presentation):最终表达的定位与边界

> 运行时面对的是玩家,需要页面来展示世界;**页面本身是资产的一部分**。

### 7.1 定位

- **表现层 = 工程的资产,不是 Runtime 的内置功能**:立绘、对话框、背景、
  音效触发器、UI 控件等都是 Presentation Graph 的产物(内核、编辑器与
  运行时文档 §6),作为资产被工程携带、被 Host 装载、被 Runtime 渲染;
- **编辑器与运行时是同一系统的两种输出形态**:编辑器面对开发者(创作与
  预览),运行时面对玩家(最终表达)——如同游戏引擎的编辑器视口与打包后
  的运行窗口。内部一致(共享内核、共享资产系统、共享工程装载路径),
  差别只在 I/O 表面与表现配置;
- **页面编辑系统暂不建立**:表现资产先用结构化格式定义(预留位置与边界),
  具体编辑工具与实现后置。

### 7.2 职责分配

| 环节 | 层 |
|------|-----|
| 表现语义(状态 → 表现的映射节点) | 内核(Presentation Graph 节点,收敛为 Text / Image / Audio / Video / Control / Scene / Composite) |
| 表现资产格式(页面 / 立绘 / 对话框 / 触发器定义) | 资产类型层(预留,格式待裁定) |
| 表现资产编辑(可视化) | 编辑器(暂无专门页面编辑系统,预留) |
| 表现资产打包 | 协议层容器 + 资产类型层组装(与一切资产同构) |
| 结构化输出事件与渲染 | Runtime(scene.update / character.dialogue 等输出事件,前端渲染) |
| 装载与装配 | Host |

### 7.3 边界

- Runtime 不规定表现:输出结构化事件,表现如何渲染由表现资产与前端决定
  (内核、编辑器与运行时文档 §5);
- 表现层与模拟层解耦:关闭表现 ≠ 关闭状态推理(叙事引擎文档 §8);
- 扩展方向(切换立绘、播放音效、对话框组件等)一律以"表现资产 + 表现
  节点"的形态生长,不引入新的层。
