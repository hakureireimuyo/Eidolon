# 资源管理与跨层集成

> 本文档定义资源文件的**所有权模型**——谁负责存储、谁负责含义、二者如何解耦。
> 相关文档：[项目职责与能力边界](./project-responsibilities.md) · [Git 仓库管理](./git-repository-management.md)

## 1. 核心问题：一张图片有两个主人

以角色立绘为例——它是一张 PNG 图片。但：

- **作为字节**：它需要被存储、索引、校验、传输。这是纯机械操作，对 JPG 和 WAV 没有区别。
- **作为语义**：它是"立绘"而非"头像"。这个含义由角色资产定义，图片格式（PNG vs WebP）反倒是次要的。

如果让同一层同时负责两者，修改资源存储机制（比如从本地 ZIP 迁移到对象存储）就必须改动所有资产类型的代码；新增一种资产类型（比如语音）就必须重新实现资源存储逻辑。

**解耦方案**：存储归协议层，语义归资产类型层。二者通过资源 ID 关联，协议层不知道"立绘"是什么意思，资产类型层不关心字节存在哪。

## 2. 资源所有权模型

```
协议层（容器）                    资产类型层（扩展）
─────────────────                ─────────────────
管理资源清单                      声明资源语义
├── 每个资源的 ID                 ├── 哪个 ID 是什么用途
├── 字节的存储路径                 ├── 哪个 ID 是什么类型（image/audio）
├── 完整性哈希                     └── 可扩展的元数据（caption 等）
└── 不解释内容
         │                              │
         └──── 通过资源 ID 关联 ────────┘
```

- **协议层**：像个仓库管理员——知道每个箱子在哪、多重、是否完好，但不打开看里面是什么。
- **资产类型层**：像个产品设计师——知道"这个箱子里装的是立绘，那个箱子里是头像"，但不负责箱子怎么存放。

两者通过资源 ID 耦合——资产类型说"我需要一个叫 portrait 的资源"，协议层找到它并交还字节。

## 3. 写入路径（生产者）

角色创建者调用资产类型层的"组装"能力——传入角色对象和图片源文件，产出标准资产包。组装过程：

1. 资产类型层生成角色的结构化数据（JSON），声明资源的语义（`{id: "portrait", type: "image/png", purpose: "立绘"}`）
2. 协议层将结构化数据写入 `data/`，将图片字节写入 `resources/`，登记到清单

**组装是唯一同时感知两层的环节**——上层消费方此后只和资产包交互，不需要知道图片是怎么进去的。

## 4. 读取路径（消费者）

引擎运行时打开资产包，协议层交还一个通用视图：

1. 遍历清单中的数据块，按类型标签路由——`application/x-eidolon-character` 发给角色解析器
2. 角色解析器还原出角色对象，其中资源引用仍为逻辑 ID
3. 需要某个资源的具体字节时，通过 ID 向协议层请求

**消费方不需要关心资源字节是存在 ZIP 里、S3 上还是本地缓存中**——那是协议层对消费方的承诺。

## 5. data/ 与 resources/ 的分离理由

不是"代码或配置 vs 二进制"的简单二分，而是**生命周期的不同**：

| | 结构化数据 (data/) | 资源文件 (resources/) |
|---|---|---|
| 变更触发 | 修改角色设定、添加新字段 | 换一张图、换一段音频 |
| 版本关联 | 随实体版本变化 | 可独立于实体版本更新 |
| 典型大小 | KB 级 | MB-GB 级 |

如果混在一起，修改一句角色描述就要重新处理几百 MB 的资源文件。

## 6. 约束规则

| 资源类型 | 落点 | 理由 |
|---------|------|------|
| 资产类型的结构化数据 | `data/`，带类型标签 | 有明确的类型归属，协议层按标签路由 |
| 图片 / 音频 / 模型权重 / 任意二进制 | `resources/`，当不透明 blob | 无资产语义，协议层只存不管 |
| 配置文件（不属任何资产类型） | `resources/`，当 blob | 同二进制处理 |

## 7. 如何新增一种资产类型（不改协议层）

协议层不预判"哪些资产类型合法"。新增一种资产类型只需要：

1. 注册一个命名空间的类型标签（如 `application/x-eidolon-personality`）
2. 定义该资产的数据格式规范
3. 提供解析器（从数据块还原出领域对象）
4. 可选提供组装器（把领域对象粘成标准包）
5. 运行时加一条路由规则

**不需要修改协议层的任何代码**。类型标签是解耦的铰链——协议层不认识它，但能路由它。

## 8. 远期：可视化编辑器

编辑器层是底层能力的"图形化合集"——它消费协议层的容器能力、资产类型层的格式定义，但自己不重新发明任何一种。它做的事是"让使用者在界面上拖拽，背后调用底层能力生成标准包"。

开发阶段刻意将各层分开，正是为了让编辑器层未来能以依赖的形式即插即用地复用每一块底层能力。
