# 项目职责与能力边界

> 本文档说明 Eidolon 引擎生态中各层的**职责边界与设计原则**。
> 仓库管理策略见 [`git-repository-management.md`](./git-repository-management.md)；资源所有权模型见 [`resource-management.md`](./resource-management.md)。

## 1. 核心命题:稳定进核心,不稳定成扩展

Eidolon 采用多独立项目架构。拆分的根本理由不是"代码多了分文件",而是一条设计原则:

> **稳定的部分进入核心,不稳定的部分成为扩展。**

- 协议层(容器格式、数据索引、完整性校验)是稳定的——无论上层是角色、世界还是宠物,容器的工作不变。
- 运行时内核(事件调度、状态管理、消息通信)是稳定的——无论驱动的是对话、经济还是战斗,调度逻辑不变。
- 具体的资产类型(角色格式、人格模型、世界规则)是不稳定的——会演化、替换、按场景裁剪。
- 可视化的形态是不稳定的——会有多种编辑器、多种分发方式。

因此,稳定能力固化为协议层和运行时内核(极少变动),不稳定能力各自独立为扩展项目(独立演化、独立版本、独立发布)。

## 2. 层级模型

从序列化到执行,各层按"对上层知识的无知程度"排列:

```
编辑器层     使用者交互界面 —— 消费底层能力,自己不发明格式
─────────────────────────────────────────────
引擎运行时   加载资产包,按类型标签路由,驱动行为
            内核领域无知 —— 不知道"角色""世界"等概念
            内含运行时解释器:把资产数据块解释为内存对象
─────────────────────────────────────────────
资产类型层   定义具体资产种类的数据格式与解析逻辑
            每个资产类型独立项目
─────────────────────────────────────────────
协议层       容器格式、数据索引、资源管理、版本迁移
            协议无知 —— 不知道任何资产语义
```

**关键洞察**:下层不对上层的概念做任何假设。协议层不知道"角色"是什么；运行时内核不知道"人格"是什么。这和数据容器不拒绝不理解的模块、运行时也不拒绝尚未实现的扩展,是同一个哲学——见 [核心架构哲学](./design-philosophy.md) §2。

**引擎视角的三分法**:Kernel = 游戏引擎(提供"游戏可以怎样运行"的能力)；Editor = 游戏设计工具
(定义"这个游戏是什么")；Runtime = 运行游戏的框架(把项目装载进内核并运行起来的宿主层)。
Runtime 是内核的宿主层,不是内核的替代品;Runtime 提供 I/O 能力,但不规定 I/O 的语义与表现。
详见 [内核、编辑器与运行时](./kernel-editor-runtime.md)。

资产数据块 → 内存对象的**解释**发生在运行时层的解释器(`eidolon-X-service`)中,而不是格式层——格式层只定义格式,解释器才赋予运行时语义。

### 游戏引擎类比

如果你熟悉 Unity 或 Unreal:

| Unity | Eidolon |
|-------|---------|
| `.unity` / `.prefab` 文件格式 | 协议层(容器格式) |
| `Transform`、`MeshRenderer` 等内置组件 | 资产类型层(character、personality 等) |
| Unity Runtime | 引擎运行时 |
| Unity Editor | 编辑器层 |
| Asset Store | (未来的资产市场) |

格式层不关心你的 C# 脚本写了什么,这和数据容器不关心"角色 / 人格 / 记忆"语义是同一原则。

## 3. 各层设计原则

### 3.1 协议层 —— 哑容器

**定位**:引擎的项目文件格式——只管"数据如何存在",不管"数据是什么意思"。

**核心能力**:
- 容器格式:标准包(纯 ZIP)+ 分发镜像(封面图内嵌包数据)
- 数据索引:声明包内有哪些数据块和资源文件,每块带类型标签(MIME 风格,如 `application/x-eidolon-character`)和版本号
- 完整性校验:哈希验证包是否损坏
- 版本迁移基础设施

**设计边界**:
- **不拒绝未知**。任何带合法类型标签的数据块都能进包。消费方按标签自行路由——协议不预判"哪些类型是合法的"。
- **data 与 resource 分离**。结构化数据(会随版本演化)放 `data/`,不透明二进制(图片、音频)放 `resources/`。二者生命周期不同:修改角色设定不应触发几百 MB 资源的重新处理。
- **不定义任何具体资产类型的格式**。`character.json` 内部的字段是资产类型层的事,协议层只保证它能被寻址、校验、迁移。

### 3.2 资产类型层 —— 领域模型

**定位**:定义某一种资产的数据格式——"这类数据长什么样、怎么验证"。

**核心能力**:
- 格式规范(canonical schema)
- 解析与校验逻辑
- 可选的"组装"能力——把领域对象 + 资源源文件粘成一个标准包

**设计边界**:
- **每种资产类型独立成项目**。角色、人格、记忆、世界——各自演化,不互相阻塞。
- **消费侧鸭子类型**。解析器不硬依赖协议层的具体实现,只要求传入的数据满足最小接口契约(有数据块字典、每块有类型标签即可)。这允许协议层的实现被替换而不影响上层。
- **资源语义归资产类型,资源字节归协议层**。哪张图是立绘——资产类型声明；图片字节存在哪——协议层管。二者通过资源 ID 关联,而不是通过路径耦合。
- **格式层零依赖,不做运行/推理/执行**。内存对象如何被 prompt 编译、序列化,是配对的运行时解释器(`eidolon-X-service`)的事;格式层不包含任何 LLM / 运行时知识(见 §3.3 解释器子项目)。

### 3.3 引擎运行时层 —— 组合入口 + 能力子项目

**定位**:引擎的运行核心。运行时层不是一个单一项目,而是**一个组合入口(eidolon-runtime)+ 多个能力子项目**。

- **eidolon-runtime(组合入口 / 宿主层)**:装载项目、驱动运行循环、建立 I/O 通道、管理生命周期;Web 服务只是当前宿主形态。只做组合,不包含领域逻辑,**不定义 I/O 的语义与表现**(见 [内核、编辑器与运行时](./kernel-editor-runtime.md))。
- **解释器子项目**(与资产类型 X 成对的 `eidolon-X-service`,如 eidolon-character-service):把资产 X 的数据块解释为类型化内存对象,并暴露其运行时能力(prompt 编译、序列化等),供组合入口按类型标签消费。**按需存在**——不需要类型化处理的资产走通用动态资源路径,不建解释器。
- **领域能力子项目**(eidolon-mind / eidolon-world / eidolon-memory 等):各自是独立的纯库项目,实现具体的运行时能力,作为第三方库被 eidolon-runtime import 引用。各自独立发版。**现行依赖机制**:消费方 pyproject 以 git 源(pin rev)声明(cartridge / eidolon-character / eidolon-character-service 即此模式,见各消费方 `[tool.uv.sources]`)。

**eidolon-runtime 的核心能力**:
- Extension Registry:发现、加载子项目,管理生命周期
- Context Compiler:收集各子项目输出,编译为 LLM 输入
- 按类型标签将数据块路由到对应的子项目解析器
- Web 服务(当前宿主形态;输入输出形式由项目定义,见 [内核、编辑器与运行时](./kernel-editor-runtime.md) §5)

**设计边界**:
- **组合层领域无知**。eidolon-runtime 不知道"角色""世界""人格"等概念——它只知道有若干已注册的能力子项目。新增一种能力 = 新增一个子项目并注册,不动 eidolon-runtime。
- **不重新定义资产格式**。数据格式是资产类型层的职责,运行时只消费。
- **组合入口只消费解释器,不直接 import 格式层**。数据块 → 内存对象的解释由配对的 X-service 完成;组合入口按类型标签路由到解释器,格式层项目不作为组合入口的生产依赖。
- **不负责序列化**。那是协议层的职责。

详见运行时核心设计。

### 3.4 编辑器层 —— Project Authoring Environment

**定位**:项目创作环境(面向使用者的可视化工具)——消费所有底层能力,自己不发明格式;不仅编辑图与资产,还编辑输入方式、表现方式与项目组合(五个编辑域,见 [内核、编辑器与运行时](./kernel-editor-runtime.md) §3)。

**核心能力**:
- 可视化创建、编辑、预览资产
- 统一资源管理
- 一站式打包与分发

**设计边界**:
- **不重新定义资产格式**。那是资产类型层的职责。
- **不重复实现容器逻辑**。那是协议层的职责。
- **所有底层能力以依赖形式被即插即用**。

### 3.5 未来层

| 层 | 定位 | 职责简述 |
|----|------|---------|
| 人格系统 | 人格资产 + 建模/推理 | 人格格式定义、人格网络结构、训练与演化——不关心角色身份静态字段(那是角色资产的事),不关心数据怎么序列化(那是协议层的事) |
| 世界系统 | 世界资产 + 生态模拟 | 世界数据格式、多角色生态、环境状态——不定义单角色身份,不关心序列化 |

| 容器格式 / 序列化 | ✅ | | | |
| 完整性校验 | ✅ | | | |
| 资源字节存储 | ✅ | | | |
| 版本迁移基础设施 | ✅ | | | |
| 定义具体资产格式 | | ✅ | | |
| 资源语义声明 | | ✅ | | |

## 5. 跨层交互原则

1. **路由靠类型标签**。协议层的数据块带 MIME 风格类型标签；运行时按标签将数据块派发给对应的资产类型解析器。标签是整个解耦的铰链。
2. **消费侧不硬依赖**。资产类型的解析器对协议层只要求最小接口契约(鸭子类型),不直接 import 协议层的类。
3. **生产侧单一耦合点**。只有"组装"环节需要同时感知协议层和资产类型层——这是故意的,避免上层消费方被迫了解容器细节。
4. **跨层不互调**。各资产类型不通过代码互相调用,只共享"资产包"——它们共存于同一个容器,各自占一条数据块,不互相感知对方的存在。
5. **组合入口只路由,不直接消费格式层**。eidolon-runtime 按类型标签把数据块路由到配对的解释器(`eidolon-X-service`);解释器负责"数据块 → 内存对象"并暴露运行时能力,组合入口不直接 import 格式层项目。
