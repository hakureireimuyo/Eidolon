# 叙事游戏引擎架构与 AI 职责分离

> 本文档记录"纯剧情 RPG 引擎设计"与"AI 职责分离与状态共享"两轮设计对话中的**最终架构决策**(已剔除过渡讨论与被修正的方案)。它建立在 [核心架构哲学与项目定位](./design-philosophy.md)、[剧情 / 世界 / 叙事引擎](./narrative-world-engine.md)、[数据容器与项目工程层](./data-container-project-layer.md) 之上,将引擎从"概念方向"推进到"可实现的架构"。
> 运行时层相关设计见:[运行时核心设计](../runtime/eidolon-runtime/docs/runtime-core-design.md) · [状态模型、上下文管理与缓存](../runtime/eidolon-runtime/docs/state-and-context.md) · [多智能体与多模态系统](../runtime/eidolon-runtime/docs/multi-agent-multimodal.md)

## 1. 引擎定位:叙事模拟引擎

Eidolon 的目标不是"AI 剧情生成器",而是一个**可设计、可验证、可扩展的叙事模拟引擎(Narrative Simulation Engine)**。

| 类别 | 核心抽象 | 本项目 |
|------|---------|--------|
| 传统游戏引擎 | 空间 + 物理 + 渲染 | 状态 + 关系 + 事件 + 叙事生成 |
| AI 聊天系统 | 请求 → 响应 | 玩家行动|AI请求|规则自触发 → 世界状态变化 → 剧情规则 → 角色状态 → LLM 表现 |
| 本项目 | — | **规则驱动的世界模拟 + AI 叙事渲染** |

模拟对象从"空间和物理"变为"状态、关系和事件",但底层思想与现代游戏引擎一致:**开发者定义世界规则,系统按规则演化,故事自然产生**(类比 Dwarf Fortress——设计规则而非设计每个故事)。

### 核心原则

> **程序负责真实性,AI 负责表现力。**

- 系统决定"发生什么"——世界状态、事件触发、规则执行、剧情推进均由程序控制。
- AI 决定"如何表达已经发生的事情"——对话生成、动作描写、环境描写、风格转换。
- AI 不拥有世界的最终解释权。角色可以产生错误的意图,但世界不会产生错误的事实。

这一原则使剧情具备**作者控制力**(伏笔回收、角色成长弧线、事件顺序可保证)和**调试能力**(事件日志可复现)。

## 2. 世界模型:ECS 统一架构

世界中的一切都是 **Entity**,能力来自 **Component**,行为逻辑由 **System** 驱动。

| Entity | 典型 Components |
|--------|----------------|
| 角色(Alice) | Personality / Memory / Relationship / Goal / Inventory |
| 国家(帝国) | Population / Economy / Military / Politics |
| 城市(王都) | Location / Resources / FactionControl |
| 物品(钥匙) | Lockable / Usable / Carriable |
| 事件(战争爆发) | Conditions / Actions / NextNodes |

这与 [运行时核心设计](../runtime/eidolon-runtime/docs/runtime-core-design.md) §6 的 ECS 同构映射一致,但在此明确为**世界层的统一建模方式**——不仅角色是 Entity,国家、城市、物品、事件都是 Entity。这极大提高了扩展性:未来新增任何世界对象只需挂载已有或新建的 Component。

### 五个核心数据对象

引擎能否扩展,取决于这五个对象的关系定义:

| 对象 | 职责 | 谁定义 |
|------|------|--------|
| **Entity** | 世界中的一个实体 | 编辑器创建 |
| **Component** | 实体的能力切片 | 资产类型层定义格式 |
| **Variable** | 可变状态值 | 世界规则读写 |
| **Event** | 状态变化的原因与结果 | 事件系统调度 |
| **Rule** | 状态→事件的映射条件 | 世界编辑器定义 |

三个编辑器共享同一底层模型:角色编辑器创建 Entity + Component；世界编辑器创建 Entity + Rule；事件编辑器创建 Event + Condition。

## 3. 世界存储:结构化数据库 + 规则引擎

世界不是文本,而是**结构化数据 + 规则系统**。

### 静态世界数据(Project Layer)

```
World/
├── locations/        ← 地点(空间关系影响旅行、信息传播、资源分布、战争范围)
├── characters/       ← 角色(身份 / 属性 / 人格 / 记忆 / 目标)
├── items/            ← 物品
├── factions/         ← 势力
├── rules/            ← 世界运行规则
└── variables/        ← 全局变量
```

### 世界规则系统(World Rule Engine)

规则不是剧情,而是"世界物理法则":

```
Condition(当前状态) → 匹配规则 → 产生事件 → 修改状态
```

例:`time >= 22:00 ∧ location == forest → spawn(wolf)` 是规则,不是写死的剧情。

### World Tick(时间系统)

时间推进类似游戏引擎的 Update Loop:

```
每经过一天 → 季节变化 → 农业产量变化 → 经济变化 → 社会状态变化 → 事件检查
```

四季更迭、经济周期、政治波动等都是 World Tick 的产物,由规则系统驱动。

## 4. 剧情作为事件图(Event Graph)

剧情不是线性文本,不是固定分支树,而是**由条件触发的事件图**。

| 传统剧情 | 本引擎 |
|---------|--------|
| 第一章 → 第二章 → ...(线性) | 事件节点 + 条件 + 动作 + 后续节点(图) |
| 分支树(A/B 二选一,规模膨胀) | 事件图(世界状态变化触发新事件,网络结构) |
| 玩家必须完成才能推进 | 玩家可忽略、利用、或反向操作 |

### 事件节点结构

```json
{
  "id": "meet_old_man",
  "condition": { "location": "village" },
  "actions": ["start_dialogue", "modify_state"],
  "choices": [
    { "choice": "help", "effects": ["increase_relation", "give_map"], "next": "forest_path" },
    { "choice": "leave", "effects": ["close_quest"], "next": "city_path" }
  ]
}
```

### 关键性质

- 剧情是**触发器**,不是强制流程。满足条件时触发特殊事件,进而改变后续输出。
- 玩家如何选择或完全不按剧情来都是允许的。
- 多路线是"规则生成"而非"预写死"——敌人存活后几十小时可能成为盟友 / 背叛者 / 最终 Boss / 被其他势力杀。

这与 [剧情 / 世界 / 叙事引擎](./narrative-world-engine.md) §3-4 一致,在此补充事件图的数据结构与非阻塞特性。

## 5. 三大编辑器

编辑器是引擎的关键产品(类比 Unreal Editor / Unity Editor),而非附属工具。开发者通过编辑器定义一个可运行的世界模型。

### 5.1 角色编辑器:定义"世界中的智能实体"

角色数据分五层:

| 层 | 变化频率 | 内容 | 用途 |
|----|---------|------|------|
| 身份层(Identity) | 不可变 / 低频 | 姓名、种族、年龄、职业、社会身份 | 角色模板 |
| 属性层(Attributes) | 低频 | 力量、智力、魅力、财富等数值 | 规则判断(如外交成功概率 = 魅力 × 信任 × 政治环境) |
| 人格层(Personality) | 静态 | 勇敢、谨慎、自私、诚实等结构化数值 | AI 输出依据(非提示词) |
| 记忆层(Memory) | 动态 | 事件记录 + 重要性评分 | 长期状态 |
| 目标层(Goal) | 动态 | 当前目标类型 + 目标对象 | 角色非剧情木偶——剧情改变环境,角色自行决策 |

> 人格不是提示词,是结构化数据。LLM 读取 `Alice: 勇敢80 / 谨慎30 / 诚实90 / 当前恐惧70` 后生成符合状态的语言。

### 5.2 世界编辑器:定义"模拟规则"

```
World
├── Geography      ← 地理系统(空间关系)
├── Society         ← 社会结构
├── Economy         ← 经济系统
├── Time            ← 时间系统(World Tick / 四季更迭)
├── Rules           ← 世界规则(冬季粮食产量下降30% / 战争状态商队减少)
└── Resources       ← 资源系统
```

### 5.3 事件编辑器(Event Editor)

"剧情编辑器"更准确的名称是**事件编辑器**,因为剧情只是事件组合。编辑器提供事件图的节点编辑:

- 事件节点、选择节点、条件节点、奖励节点、状态修改节点
- 连线:事件 A → 条件 → 事件 B

### 5.4 三编辑器共享底层模型

不要将三个编辑器设计为三个独立工具。底层统一为 Entity / Component / Variable / Event / Rule / Resource,各编辑器只是对同一模型的不同视图。

## 6. Action Intent → World Event 循环

这是引擎最有价值的"游戏引擎"部分——**角色认知世界**与**世界实际运行**的分离。

```
                ┌──────────────────┐
                │   World State    │
                │  时间/物品/角色   │
                │  关系/规则/事件   │
                └────────┬─────────┘
                         │ 提供事实
                         ↓
                ┌──────────────────┐
                │  Character AI    │
                │  感知→思考→意图  │
                │      ↓           │
                │    表现输出       │
                └────────┬─────────┘
                         │ Action Intent
                         ↓
                ┌──────────────────┐
                │  World Runtime   │
                │  验证/执行/结算   │
                └────────┬─────────┘
                         │ World Event
                         ↓
                ┌──────────────────┐
                │  Character AI    │
                └──────────────────┘
```

### 执行流程

1. **Character AI** 产生行动意图(Intent),不直接决定结果:
   ```json
   { "intent": { "action": "open_door", "target": "room_102" },
     "output": { "dialogue": "我进去看看。", "expression": "谨慎" } }
   ```

2. **World Runtime** 验证并执行世界规则:
   ```
   门存在？ ✓    门锁定？ ✓    角色有钥匙？ ✗
   ```

3. 产生**客观世界事件**:
   ```json
   { "event": "action_failed", "actor": "alice",
     "action": "open_door", "target": "room_102", "reason": "locked" }
   ```

4. 结果返回 Character AI,角色据此继续推理。

> **角色可以产生错误的意图,但世界不会产生错误的事实。**

这比让 LLM 自己维持世界状态可靠得多——LLM 不再拥有世界的最终解释权。

## 7. AI 职责分离

### 7.1 表现层职责可统一(修正)

早期设想"对话 AI / 动作神态 AI / 环境 AI"各为独立 AI。经讨论修正:**表现层职责可由同一角色 AI 通过结构化输出一次性完成**,无需多余的上下文复制。

角色 AI 统一输出:

```json
{
  "intent": { "action": "...", "target": "..." },
  "dialogue": "...",
  "action": "...",
  "expression": "...",
  "environment": "..."
}
```

Runtime 根据表现配置决定最终展示哪些字段(见 §8)。

### 7.2 真正需要分离的:角色认知 vs 世界运行

真正值得拆开的不是表现层职责,而是:

| 链 | 职责 | 谁执行 |
|----|------|--------|
| 角色认知链 | 感知 → 思考 → 意图 → 表现 | Character AI |
| 世界运行链 | 验证 → 执行 → 结算 → 事件 | World Runtime(程序 + 子 AI) |

角色 AI 只提出"我想做什么",不决定"做了之后结果如何"。

### 7.3 两类 AI

| 类型 | 职责 | 输出 |
|------|------|------|
| **状态推理器** | 改变 Runtime 中的结构化状态 | 进入 State Store,不直接生成玩家文本 |
| **表现生成器** | 读取状态并生成最终表现 | 进入 Presentation 层 |

状态推理器(EmotionAI / MemoryAI / RelationshipAI / WorldStateAI / PlotAI)的结果应尽可能进入统一状态；表现生成器(DialogueGenerator / ActionGenerator / EnvironmentGenerator)读取状态并生成文本。

### 7.4 子 AI 作为 Runtime 工具

Character AI 可向 Runtime 请求调用子系统能力:

```
Character AI
    ├── 请求:查询物品    → World AI → 结构化结果
    ├── 请求:判断行动    → Combat System → { hit, damage, target_state }
    ├── 请求:推进剧情    → Plot System → 事件结果
    └── 请求:生成 NPC 行为 → NPC AI → 行为数据
```

**关键认知**:不是所有"子 AI"都是 LLM。距离计算、碰撞、物品数量、金钱、HP、时间、状态机、规则判断应该是纯程序；NPC 战术、复杂社会行为、剧情事件解释、模糊世界推理才适合交给 AI。最终系统是**混合式世界模拟器**,而非"多个 LLM 拼接"。

## 8. 表现层与模拟层解耦

### 表现层开关

```
普通模式:     dialogue ✓  action ✓  expression ✓  environment ✓
纯聊天模式:   dialogue ✓  action ✗  expression ✗  environment ✗
```

Runtime 根据配置决定调用哪些表现生成器。模拟手机聊天时只保留对话,UI 变为纯聊天消息。

### 关键约束:关闭表现 ≠ 关闭状态推理

```
角色心理状态 → Runtime → ┌─ 对话 AI → 文字
                         └─ 神态 AI → 表情(可关闭)
```

关闭神态 AI 时:
- ✅ 神态表现 = 不生成
- ❌ 角色心理状态 ≠ 不存在

手机聊天模式下玩家看不到角色表情,但角色的"紧张程度"仍然影响对话生成。**表现层与模拟层解耦**是核心架构约束。

### 模型无需感知表现配置

模型输出结构保持不变,UI 直接忽略不需要的字段。后续可优化:Runtime 告知模型 `requested_output: [dialogue]`,让模型不生成其他字段以节省 token——但这属于优化,非架构必要条件。

## 9. 上下文管理升级:双维度模型

### 修正:从"按频率分层"到"双维度管理"

[状态模型、上下文管理与缓存](../runtime/eidolon-runtime/docs/state-and-context.md) §4 已定义按更新频率分四层(静态 / 低频 / 中频 / 高频)。该模型的隐含前提是**一个 AI 需要同时承担所有职责**,因此需要通过频率划分减少上下文重复。

架构变化后(AI 不再是世界的承载者,而是 Runtime 中的推理节点),提示词管理应从"按信息生命周期管理"转变为增加**数据所有权**维度:

| 维度 | 含义 | 示例 |
|------|------|------|
| **数据生命周期**(已有) | 信息变化的频率 | 静态(人格)/ 低频(关系)/ 中频(情绪)/ 高频(对话) |
| **数据所有权**(新增) | 谁拥有、谁可修改 | 角色人格(Owner: Character Data)/ 角色情绪(Owner: Character Runtime, Modifier: Character AI)/ 房间状态(Owner: World Runtime)/ 剧情阶段(Owner: Plot Runtime) |

> **核心约束**:角色 AI 看到的信息 ≠ 角色 AI 可以修改的信息。

角色看到 `天气:暴雨`,但不能输出 `{ "weather": "晴天" }` 改变天气。它只能产生 `{ "intent": "寻找避雨地点" }` 交给世界系统。

### 上下文 = Runtime 投影

```
完整状态数据库 → 权限过滤 → 任务投影 → 生成上下文 → 发送给 AI
```

不同 AI 从 Runtime 获取自己的视图,而非接收统一的巨型上下文:

| AI | 需要知道 | 不需要知道 |
|----|---------|-----------|
| Character AI | 角色人格 + 自身状态 + 感知信息 + 最近事件 + 当前任务 | 整个世界地图 / 所有 NPC 状态 / 全部历史 |
| World AI | 世界规则 + 当前世界状态 + 行动请求 + 相关实体 | 角色完整心理 / 说话风格 / 过去聊天 |
| Plot AI | 剧情目标 + 重要事件历史 + 关系变化 + 当前阶段 | 具体对话内容 |

### Prompt 结构

```
Prompt Builder
├── Agent Identity       ← 当前 AI 的职责定义
├── Capability Rules     ← 可以做什么、不可以做什么
├── Runtime Projection   ← 从世界状态投影的数据
└── Task Input           ← 当前请求
```

而非"你是 Alice,这里是整个世界……请继续聊天"。

> **上下文不是被压缩和保存的文本,而是 Runtime 根据 Agent 身份生成的数据视图。** 前者在解决 LLM 的限制；后者在设计一个真正的智能系统。

## 10. 技术栈选择:Python + Web UI

### 为什么不用现有游戏引擎

Unity / Unreal / Godot 的核心能力是渲染、动画、物理、音频、场景管理。本项目的核心问题是世界状态管理、规则执行、事件调度、角色状态变化、自然语言生成。直接使用游戏引擎会**被迫把世界模型适配到为三维空间设计的模型中**,增加无关复杂度。

### Python 适合第一阶段 Runtime

核心运行过程(读数据 → 构建状态 → 执行规则 → 触发事件 → 更新状态 → 调用模型生成文本)本质是数据处理、状态机、规则计算、AI 调度——Python 在这些领域成熟。

### Web UI 适合编辑器前端

编辑器本质是数据库管理器 + 流程编辑器 + 状态调试器 + 节点编辑器,Web 技术非常适合。

### 架构边界:为未来迁移留空间

```
Web UI → Python Runtime → Data Model / Rule Engine / Event System / AI Interface → Storage Layer
```

未来 Rule Engine / Event System / Simulation Core 可迁移到 Rust / C++ / Go,而不用推翻整个设计。因此从一开始保持层边界,不把所有东西永远绑定 Python。

### 避免过早引入复杂框架

项目核心价值在**模型设计 + 运行机制 + 数据协议**,不在前端框架 / 服务器框架 / 数据库框架。第一阶段技术栈足够精简:

- Python:标准库 + pydantic + pytest
- Web:FastAPI + React
- 甚至第一版 FastAPI + React 即可

## 11. 开发阶段建议

| 阶段 | 目标 | 核心实现 |
|------|------|---------|
| 第一阶段 | 剧情播放器 | 加载剧情文件 → 显示文本 → 玩家选择 → 修改变量 → 进入下一事件(类似视觉小说引擎,不含 AI) |
| 第二阶段 | 加入世界状态 | 变量系统 + 条件判断 + 事件触发器 + 存档 |
| 第三阶段 | 角色模拟 | 人格 + 记忆 + 关系 + 目标 |
| 第四阶段 | AI 表现层 | 动态对白 + 动态描述 + 图片生成 + 声音生成 |

> 不建议从零直接做完整 RPG。按引擎开发顺序逐层验证。

## 12. 修正与被推翻的观点

| 被修正 / 推翻 | 最终决定 |
|--------------|---------|
| "对话 AI / 动作 AI / 环境 AI" 各为独立 AI | 表现层职责可由同一角色 AI 通过结构化输出完成；真正需要分离的是角色认知 vs 世界运行 |
| 提示词按更新频率分层(单一维度) | 增加数据所有权维度:双维度模型(生命周期 + 所有权) |
| 上下文 = 压缩后的文本 | 上下文 = Runtime 根据 Agent 身份投影的数据视图 |
| AI 负责创造剧情 | AI 负责"表达已经发生的事情"；程序负责"决定发生什么" |
