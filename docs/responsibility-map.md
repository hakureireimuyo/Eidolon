# 职责地图:正交维度与依赖轴

> 本文档回答一个问题:**Eidolon 的各部分如何共处而不互相污染?**
> 答案不是"自底向上的分层",而是十个部分占据数据、语义、能力、执行、装配、
> 表达等**正交维度**;理解系统的钥匙是依赖方向、所有权、生命周期与
> "允许知道什么",而不是层级位置。
> 相关文档:[核心架构哲学](./design-philosophy.md) · [项目职责与能力边界](./project-responsibilities.md) ·
> [能力定位:实现层分配](./capability-placement.md) · [宿主开发总纲](../host/docs/host-development.md)

## 1. 核心认知:正交维度,不是分层

把各部分强行理解成"核心层 → 业务层 → UI 层"会导致职责漂移——最终要么
"所有东西都变成 Host 功能",要么"所有东西都塞进内核"。正确的读法是:
每个部分回答一个**正交的问题**。

| 部分 | 核心问题 | 允许知道什么 |
|------|---------|-------------|
| 协议层(Cartridge) | 数据如何物理承载与恢复 | 不理解具体语义 |
| 资产类型层(asset-types) | 数据是什么 | 定义资产语义 |
| 资产系统(Asset System) | 资产如何在世界中存在、加载、引用、管理 | 深度参与内核 / 编辑器 / 运行时 |
| 能力库(capabilities) | 能力如何实现 | 不依赖内核 |
| Host | 如何把各种实现装配成一个可运行系统 | 组合根 |
| 内核(Kernel) | 图世界如何按冻结语义执行 | 不知道具体能力 |
| 编辑器(editor) | 开发者如何创建、观察、修改世界 | 与运行时共享世界 |
| 运行时(runtime) | 玩家如何运行和观察世界 | 与编辑器共享世界 |
| 表现层(Presentation) | 世界如何最终呈现给用户 | 独立的表现领域 |
| 插件系统(Plugin System) | 如何发现、加载、分发扩展 | 暂只预留边界 |

## 2. 四条依赖轴(取代单一树)

**数据轴:**

```text
Asset Type → Asset → Cartridge
```

**执行轴:**

```text
Capability → Host Adapter → NodeType → Kernel
```

Kernel 向 NodeType 消费语义,具体实现由 Host 装配提供。

**创作 / 运行轴:**

```text
                 Shared World
                /            \
            Editor          Runtime
          (开发者视图)      (玩家视图)
```

**表达轴:**

```text
World State / Events → Presentation → Final User Experience
```

插件系统横跨其中,负责把外部实现带入 Host:

```text
Plugin → Capability / Asset Type / Node Provider → Host → Eidolon World
```

## 3. 关键裁定

### 3.1 协议层是物理承载协议,不是资产系统

协议层对数据的形式完全不敏感。某种数据进入容器的条件只有四条:

1. 唯一的类型声明;
2. 对应的序列化 / 反序列化协议;
3. 必要的依赖描述;
4. 注册到资产类型系统。

因此用户资产、自定义脚本、图、节点定义、插件包、未来存档——都不需要为
"进入工程包"重新设计物理格式,它们最终都是容器中的不同资产条目。
**新增资产类型不迫使协议层发生变化**;"数据是什么"(资产类型层)与
"数据如何被运输 / 保存"(协议层)彻底分离。

### 3.2 能力轴依赖方向(冻结)

```text
Capability → Host(adapt / bind)→ NodeType → register → Kernel
```

- 依赖方向是 **Kernel ↑ Host ↑ Capabilities**,不是"Kernel → Capability"
  也不是"Capability → Kernel"——后两者都会让内核产生对具体能力的知识;
- "封装为节点"的精确含义是**协议适配与装配**:Capability 仍是底层能力
  实现,Node 是内核世界里的语义接口,Host 把前者装配成后者;
- 内核看到的贫瘠世界只有:NodeType / Graph / Connection / State / Event /
  AssetRef。它不应该知道 Plugin / Provider / Capability / Package /
  Project / Host / Editor / Runtime——这些都是内核之外的组合概念。

### 3.3 内核完全不知道插件

插件的发现、加载、解析一律在内核之外:

```text
Plugin System → 发现/加载能力包 → Host → 注册 NodeType → Kernel
```

冻结内核的真正意义:**内核不是整个 Eidolon 的核心业务,而是整个 Eidolon
可以依赖的最小语义机器。**

### 3.4 编辑器与运行时是同一系统的两个投影

- Editor = "这个世界在创作者手中是什么样";Runtime = "这个世界在最终
  用户手中是什么样"(类比游戏引擎的 Scene View 与最终游戏窗口);
- 原则:**Editor 不重新实现一套 Runtime 语义来做预览——Editor 运行同一
  套世界,只是在其上增加编辑能力与开发者观察能力**;
- 两者共享:内核、资产系统、工程表示、图表示、表现表示。不允许出现
  "编辑器资产系统 / 运行时资产系统"两套实现,否则迟早出现"编辑器里能
  运行,打包后行为不同"。

### 3.5 资产系统是编辑器与运行时的共同世界基础

资产系统尚未实现,但它不是普通业务模块,而是**与内核同一基础设施级别、
被编辑器与运行时共享的世界基础**。三个边界必须保持:

```text
Asset System   管理"资产作为世界对象如何存在"(身份/类型/生命周期/依赖/
               引用/加载/解析/创建/序列化/所有权/运行时表示/编辑表示/持久化)

Asset Types    定义"某一种资产是什么"

Capabilities   提供"某种能力如何实现"
```

### 3.6 表现层是独立领域,不是 Runtime 的 UI

运行时最终要把世界表达出来(立绘、对话框、背景、文本、音效、动画、UI、
按钮、场景切换、视觉效果),这构成独立的 **Presentation Domain**——
Eidolon 的最终表达系统。未来形态可扩展为:表现资产 / 表现节点 / 表现状态 /
表现事件 / 表现绑定 / 表现编辑器 / 表现渲染器。例如"角色说话"是一条
世界层链路:

```text
Character.Dialogue → Presentation Event → Dialogue Component
→ Character Portrait → Text Rendering → Audio
```

新增任何表现形态(立绘、动画、声音、摄像机、UI、过场)都不修改 Runtime
的核心定义。页面编辑系统的未来定位不是"网页编辑器",而是表现领域的编辑
工具(后置)。

## 4. 当前冻结:职责地图,而非实现

- **冻结对象**:本职责地图 + 依赖方向 + 所有权 + 生命周期 + "允许知道什么";
- **暂不实现**:页面系统、插件系统、资产系统 API;
- 下一步的问题已经从"如何实现一个图运行时"变为:**如何定义一个可以无限
  扩展、但扩展不会反过来污染最小语义核心的系统。**
- 已有的验证期实现(如编辑器内嵌引擎)与本地图的关系:短期交叉照旧,
  最终收敛到本文档边界(宿主开发总纲 §6)。
