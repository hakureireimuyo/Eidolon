# 环境隔离与虚拟环境归属策略

> 本文档规定 Eidolon 生态下**虚拟环境(venv)该存在于何处**——尤其是未来子项目不断增多时的统一策略。
> 相关文档:[项目职责与能力边界](./project-responsibilities.md) · [资源管理与跨项目集成](./resource-management.md) · [Git 仓库管理](./git-repository-management.md)

> **落地方式(2026-08 更新)**:本文的**分层原则依然有效**(库项目零/轻依赖、重依赖只出现在应用层)。
> 执行方式为**各仓库独立环境**:每个仓库都是独立 uv 项目,应用 / 服务仓持有自己的
> `.venv` 与 `uv.lock`;兄弟库以 **git 源(pin rev)** 作为第三方依赖被安装,
> 不存在顶层 uv workspace 与共享 `.venv`(monorepo 检出与单独 clone 行为一致)。
> 具体操作见 [`agent-conventions/uv-dependency-management.md`](../agent-conventions/uv-dependency-management.md)。
> 库项目目录下**不应出现 `.venv` 或 `requirements*.txt`**;应用 / 服务仓的 `.venv` 已 gitignore。

## 1. 核心原则

**虚拟环境是「依赖隔离 / 部署边界」机制,不是「仓库边界」机制。**

因此,venv **不随仓库数量走**,而跟随两件事走:

1. **依赖足迹**——项目是否真的引入了第三方依赖；
2. **消费 / 部署边界**——谁在运行、谁在部署。

在我们的多仓库架构里,绝大多数底层项目是「库」而非「应用」:它们被 `pip install` 进某个消费方环境,自己并不运行在独立环境里。所以**下层项目默认不持有 venv**。

## 2. 决策规则

| 项目类型 | 是否持有 venv | 理由 |
|---------|:------------:|------|
| 资产格式层(协议层) | 不持有 | stdlib only,零第三方依赖 |
| 资产类型层 | 常态不持有 | 设计为轻 / 零依赖的库,被安装进消费方 |
| 某库真的引入重依赖时 | 仅临时 / 测试用 | 自身开发测试可建一次性环境,但不要求消费方共享 |
| 可独立部署的应用 / 服务 | 由统一管理器提供 | 重依赖集中于此 |

**一句话**:下层是库,被装进上层；venv 只存在于「消费边界」(可独立部署的应用 / 服务)。

## 3. 为什么不为每个仓库建 venv(尤其项目变多后)

1. **N 份重复重依赖**:若 torch、某个 Web 框架被 5 个项目各装一份,磁盘与安装时间爆炸。
2. **版本漂移冲突**:项目 A 要 `numpy<2`、项目 B 要 `numpy>=2`,各自 venv 能装但整体不一致,出问题难排查。
3. **心智负担**:N 个仓库 N 个环境,激活来激活去。

## 4. 映射到三层架构

```
┌─────────────────────────────────────────────────────────────┐
│ 编辑器层 / 引擎运行时(应用 / 服务)                            │
│   消费边界 —— 重依赖(Web / GUI / ML)集中于此                  │
├─────────────────────────────────────────────────────────────┤
│ 资产类型层(库)                                              │
│   轻 / 零依赖 · 无独立环境 · 被安装进上层应用                  │
├─────────────────────────────────────────────────────────────┤
│ 资产格式层(库)                                              │
│   stdlib only · 无需独立环境 · 被安装进消费方                 │
└─────────────────────────────────────────────────────────────┘
```

箭头方向:应用层的 venv **向下依赖并安装** 扩展层与协议层,而非反过来。

> 这与「可视化统一操作项目(eidolon-studio)」的远期方向天然吻合:Studio 是面向使用者的唯一消费边界,所有底层能力以依赖形式被它即插即用,底层无需各自再备一份环境。

## 5. 现在 vs 未来

- **现在**:协议层与资产类型层均为零或极轻依赖,不需要独立环境。每个仓库是独立 uv 项目,应用 / 服务仓各自 `uv sync` 维护自己的 `.venv` 与 `uv.lock`;兄弟库经 git 源(pin rev)安装。
- **未来子项目变多**:套用上面的边界规则。重依赖集中在应用层;跨仓库版本一致性由 git 源 pin rev + 各仓 `uv.lock` 保障,而不是给每个库各开 venv。

## 6. 冻结约定

> 1. 库项目(协议层 / 资产类型层)保持零或极小依赖集。
> 2. 重依赖只出现在应用 / 服务类项目。
> 3. 环境只存在于消费边界(应用 / 服务仓),由各仓 uv 独立维护。
> 4. 跨仓库版本一致性,由 git 源 pin rev + 各仓 uv.lock 保障,而非各库自带环境。
