# 环境隔离与虚拟环境归属策略

> 本文档规定 Eidolon 生态下**虚拟环境（venv）该存在于何处**——尤其是未来子项目不断增多时的统一策略。
> 相关文档：[项目职责与能力边界](./project-responsibilities.md) · [资源管理与跨项目集成](./resource-management.md) · [Git 仓库管理](./git-repository-management.md)

> **落地方式已更新**：本文的**分层原则依然有效**（库项目零/轻依赖、重依赖只出现在应用层），
> 但"应用层各自持有 venv"这一**执行方式**已被 uv workspace 取代——
> 仓库根目录统一一个 `.venv`，所有子项目 editable 安装其中，版本由 `uv.lock` 锁定。
> 具体操作见 [`agent-conventions/uv-workspace-management.md`](../agent-conventions/uv-workspace-management.md)。
> 子项目目录下**不应再出现 `.venv` 或 `requirements*.txt`**。

## 1. 核心原则

**虚拟环境是「依赖隔离 / 部署边界」机制，不是「仓库边界」机制。**

因此，venv **不随仓库数量走**，而跟随两件事走：

1. **依赖足迹**——项目是否真的引入了第三方依赖；
2. **消费 / 部署边界**——谁在运行、谁在部署。

在我们的多仓库架构里，绝大多数底层项目是「库」而非「应用」：它们被 `pip install` 进某个消费方环境，自己并不运行在独立环境里。所以**下层项目默认不持有 venv**。

## 2. 决策规则

| 项目类型 | 是否持有 venv | 理由 |
|---------|:------------:|------|
| 资产格式层（PersonaSeed） | ❌ 不持有 | stdlib only，零第三方依赖 |
| 资产类型层（eidolon-character / +N 模块） | ❌ 常态不持有 | 设计为轻 / 零依赖的「库」，被安装进消费方 |
| 某库真的引入重依赖时（如 eidolon-mind 训练用 torch） | ⚠️ 仅临时 / 测试用 | 自身开发测试可建一次性 venv，但不要求消费方共享 |
| 可独立部署的应用 / 服务（studio、runtime、mind 训练服务） | ✅ 各自一个 | 重依赖（Web / GUI / ML）集中在此 |

**一句话**：下层是库，被装进上层；venv 只存在于「消费边界」（可独立部署的应用 / 服务）。

## 3. 为什么不为每个仓库建 venv（尤其项目变多后）

1. **N 份重复重依赖**：若 torch、某个 Web 框架被 5 个项目各装一份，磁盘与安装时间爆炸。
2. **版本漂移冲突**：项目 A 要 `numpy<2`、项目 B 要 `numpy>=2`，各自 venv 能装但整体不一致，出问题难排查。
3. **心智负担**：N 个仓库 N 个环境，激活来激活去。

## 4. 映射到三层架构

```
┌─────────────────────────────────────────────────────────────┐
│ 编辑器层 / 引擎运行时（应用 / 服务）                            │
│   eidolon-studio  · eidolon-runtime · eidolon-mind(training) │
│   └── 各自拥有 venv，pip 安装下面各层作为依赖                   │
│       重依赖（Web / GUI / ML）集中于此                        │
├─────────────────────────────────────────────────────────────┤
│ 资产类型层（库）                                              │
│   eidolon-character / +N 模块                                 │
│   └── 轻 / 零依赖 · 无独立 venv · 被安装进上层应用            │
├─────────────────────────────────────────────────────────────┤
│ 资产格式层（库）                                              │
│   PersonaSeed                                                 │
│   └── stdlib only · 无需 venv · 被安装进消费方               │
└─────────────────────────────────────────────────────────────┘
```

箭头方向：应用层的 venv **向下依赖并安装** 扩展层与协议层，而非反过来。

> 这与「可视化统一操作项目（eidolon-studio）」的远期方向天然吻合：Studio 是面向使用者的唯一消费边界，所有底层能力以依赖形式被它即插即用，底层无需各自再备一份环境。

## 5. 现在 vs 未来

- **现在**：两个项目均为零依赖（`dependencies = []`），连 venv 都不需要。开发期把 PersonaSeed 用 editable 安装进一个共用的 dev venv，或直接 `sys.path`（当前示例做法）即可。
- **未来子项目变多**：套用上面的边界规则。重依赖集中在应用层；若想要隔离又不想重复安装，可在应用层用 `uv` / `pip-tools` 做跨仓库的**统一版本锁定（constraints）**，而不是给每个库各开 venv。

## 6. 冻结约定（新增子项目时照此执行）

> 1. 每个**库项目**（资产格式层 / 资产类型层）的 `pyproject.toml` 保持 `dependencies = []`（或极小依赖集）。
> 2. **重依赖只出现在「应用 / 服务」类项目**的 `pyproject.toml` 中。
> 3. 应用 / 服务类项目把各子项目列为依赖（可指向 git / submodule 路径，如 `personaseed @ git+https://...` 或本地路径）。
> 4. venv **永远只存在于消费边界**（可独立部署的应用 / 服务）。
> 5. 跨仓库版本一致性，由应用层的统一约束锁（uv / pip-tools）保障，而非各库自带 venv。
