# Agent 规范 —— 从 PersonaSeed 文档审查中总结

## 审查过程概述

PersonaSeed 设计文档经过了多轮审查，发现并修正了以下问题：

| # | 问题 | 表现 | 修正 |
|---|------|------|------|
| 1 | **边界越界** | 文档中定义了 Character Engine、LLM Adapter、人格推理等运行时逻辑 | 删除全部运行时内容，明确 PersonaSeed 是纯数据层 |
| 2 | **方案罗列** | PNG 容器方案列出了 A/B/C 三种对比，而决策早已做出 | 只保留最终方案（cPKG chunk + ZIP），删除对比讨论 |
| 3 | **临时方案** | `big_five` 作为人格网络的临时替代字段存在于 character.json | 删除临时字段，不做任何过渡性实现 |
| 4 | **提前定义** | 人格模型的 MLP 结构、输入输出维度、权重布局被提前规定 | 简化为边界文档，只声明目录存在，具体设计归 Eidolon Mind |
| 5 | **提前定义** | 扩展模块的 JSON Schema、SQL DDL、状态机图被提前规定 | 简化为方向列表 + manifest 声明格式 |
| 6 | **跨层混入** | Git 仓库管理策略写在 PersonaSeed 的设计决策中 | 移至 Eidolon 层级的独立文档 |
| 7 | **核心模糊** | 数据访问接口被定位为"工具集"（toolkit），像是附属品 | 重新定位为项目核心产出：`seed.open()` 就是 PersonaSeed |

## 为什么会发生这些问题

### 根本原因：两种思维模式的偏差

Agent 默认遵循的是**"全面实现"思维**：

```
需求 → 尽可能填充细节 → 提供过渡方案 → 包含实现参考 → 呈现所有选项
```

但本项目的开发哲学是**"精确边界"思维**：

```
需求 → 确定边界 → 只定义规格 → 不留临时方案 → 不提前实现 → 只呈现决策
```

### 具体偏差分析

#### 偏差 1：越界——"帮上层也做了"

Agent 的隐含假设是文档应覆盖整个生态的运行逻辑，但实际每个项目只负责自己的层级。

**错误**：PersonaSeed 文档包含 Character Engine、LLM Adapter、人格推理——这些都该由上层项目负责。
**正确**：PersonaSeed 只定义数据格式 + 数据访问接口。上层如何使用数据，不是 PersonaSeed 的事。

```
Agent 思维：  PersonaSeed ─── 延伸覆盖 ───→ Runtime / LLM
正确边界：    PersonaSeed ─── 数据接口 ───│← 上层项目
```

#### 偏差 2：填充——"帮未来做了决定"

Agent 倾向于为未来模块预定义结构（网络层数、输入维度、SQL Schema），但这实际上是在替尚未启动的子项目做设计决策。

**错误**：在 PersonaSeed 文档中规定了人格网络的 MLP 结构、记忆数据库的 SQL Schema。
**正确**：PersonaSeed 只声明模块目录存在，内部格式由对应子项目自己定义。

#### 偏差 3：过渡——"先用简单的代替"

Agent 倾向于在正式方案就绪前提供临时替代品，但这会引入技术债务。

**错误**：`big_five` 字段作为人格网络的临时替代放在 character.json 中。
**正确**：宁愿没有，也不要有临时方案。等到人格模块真正启动时一次性实现。

> 临时方案的问题：
> - 消费方可能依赖临时格式，正式方案推出时产生迁移成本
> - 临时字段的语义和正式方案的语义不同，迁移不只是一一映射
> - 临时方案的存在会降低实现正式方案的紧迫性

#### 偏差 4：选项罗列——"让用户再看看"

Agent 倾向于在设计文档中罗列多个方案并分析优劣，但本项目的讨论阶段已经结束——文档应记录的是**已做出的决策**，而非重新讨论。

**错误**：PNG 容器方案列出 A/B/C 三种对比。
**正确**：只写最终选定的方案（cPKG chunk + ZIP），被排除的方案简单说明即可。

#### 偏差 5：层级混淆——"放在哪里都行"

Agent 没有仔细区分哪些决策属于哪个层级。Git 仓库管理策略属于 Eidolon 顶层，不应出现在 PersonaSeed 子项目的设计决策中。

**错误**：`10-design-decisions.md` 中包含 Monorepo vs Submodule 的决策。
**正确**：该决策属于 `Eidolon/docs/git-repository-management.md`。

## 应遵守的规范

### 规范 1：边界优先

在编写任何文档或代码之前，首先明确当前项目的职责边界。问自己：

- 这件事是本项目的职责，还是上层/下层/兄弟项目的职责？
- 如果是其他项目的职责，只声明接口/位置，不定义内部实现

```
本项目负责：      定义数据格式、提供数据访问接口
上层项目负责：    消费数据、运行角色、调用 LLM
兄弟项目负责：    人格网络设计、世界模拟设计
```

### 规范 2：不做临时方案

不因为某个功能尚未就绪而提供临时替代。如果现在做不了，就留空。

- ❌ "V1 先用 big_five 代替，Phase 4 再替换为网络权重"
- ✅ "人格量化建模由 personality/ 模块承载，具体设计属于 Eidolon Mind 项目"

### 规范 3：只呈现决策，不重新讨论

设计文档记录的是**已做出的决策**，不是讨论过程。如果有多个方案曾被考虑，简要提及被排除的方案及原因即可，不应以"对比选择"的方式组织文档。

- ❌ "## 方案对比：A vs B vs C"
- ✅ "## 最终方案：C（方案 A 因 X 被排除，方案 B 因 Y 不适用）"

### 规范 4：不提前定义未确定的设计

如果某个模块尚未启动设计，文档中只声明其存在和位置，不预定义其内部结构。

- ❌ 提前写出记忆数据库的 SQL Schema、人格网络的输入维度
- ✅ 声明 `memory/` 目录存在，由未来子项目定义内部格式

### 规范 5：分清文档归属

涉及多个项目的内容，放在正确层级的文档中。

```
Eidolon/docs/           → Git 管理、生态架构、跨项目协议
PersonaSeed/docs/       → 角色数据格式、数据访问接口
Eidolon Mind/docs/      → 人格网络结构、训练策略（未来）
```

### 规范 6：项目以接口为核心

每个项目的文档应突出其核心产出：

- PersonaSeed 的核心产出 = `seed.open()` → `PersonaSeedPackage`
- 格式规范是支撑，接口是对外暴露的面

## 为什么用户能发现这些问题

用户之所以能快速发现这些不合理设计，是因为用户对项目有**清晰的边界感**：

1. **用户知道每个项目的分工**：PersonaSeed 做什么、不做什么，在项目启动时就已经确定
2. **用户对"临时方案"敏感**：长期维护项目的经验让用户清楚临时方案的真实代价
3. **用户区分"讨论"和"决策"**：讨论阶段的事情不应出现在规格文档中
4. **用户有整体架构图景**：知道 Git 管理是生态级别的事，不是子项目的事

Agent 没有这些上下文——Agent 倾向于从单个文档出发，尽可能使其"完整"，但这种完整往往意味着越界。

## 审查检查清单

今后编写文档后，用以下问题自检：

1. [ ] 文档内容是否全部在本项目的职责范围内？
2. [ ] 是否有为"以后会做的功能"预留的临时字段或结构？
3. [ ] 是否预定义了属于其他项目（或尚未启动）的模块的内部格式？
4. [ ] 设计决策部分是否只有已确定的选择，而非选项罗列？
5. [ ] 跨层级的内容（如 Git 管理）是否放在了正确的文档中？
6. [ ] 项目的核心产出（接口/数据结构）是否被突出，而非被埋没在实现细节中？
7. [ ] "运行时""推理""执行"等概念是否误入了纯数据层的文档？

## 外部审查补充（第二轮）

经过外部 AI 审查后，发现以下额外问题，补充如下规范。

### 补充规范 7：Manifest 应保持"无知"

manifest.json 是模块注册表，不是模块解释器。它不应该理解任何模块的语义。

- ❌ manifest 中维护模块类型注册表（`type: "personality"` 的 schema 是什么）
- ✅ manifest 只记录 `{id, path, type, version}`，type 是任意字符串

第三方可以添加 `type: "pokemon-system"`，PersonaSeed 不应拒绝。

### 补充规范 8：区分标准格式与分发封装

如果一个数据格式有两种存在形态（如 `.seed` 包和 `.png` 镜像），文档应明确哪一个是标准格式、哪一个是分发封装，不应将分发封装提升为核心格式。

- ❌ 文档暗示 PNG 是 PersonaSeed 的唯一存在形式
- ✅ 明确 `.seed` 是标准格式，`.png` 是为分发便利提供的封装

### 补充规范 9：区分模板定义与初始状态

角色数据应区分：
- **身份定义（模板）**：角色是谁，永久不变
- **初始配置（bootstrap）**：某次运行的起点参数

二者应有明确的术语区分和文档边界。不要让 character.json 同时承担两种角色。

### 补充规范 10：区分规范与实现

规范和参考实现应放在不同目录中，为多语言 SDK 留出空间：

```
PersonaSeed/
├── specification/        # 格式规范（语言无关）
└── toolkit/              # Python 参考实现
```

### 补充规范 11：安全模型应在第一版预留

即使 V1 不实现完整签名验证，也应在数据格式中预留安全字段（hash、signature），避免后续被迫修改格式结构。

## 第三轮补充：协议层抽象

经过第三轮讨论，发现根本问题是 PersonaSeed 的**抽象层级错误**——它把自己定位为"角色卡格式"，而实际上应该定位为"数据容器协议"。

### 补充规范 12：协议不应知道上层概念

底层协议不应该知道上层在做什么。PersonaSeed 不应该知道"角色"、"人格"、"记忆"这些概念。

- ❌ `Package.characters: dict` —— 协议预设了"角色"这个概念
- ✅ `Package.entries: dict[str, Entry]` —— 协议只知道有若干数据块

- ❌ `character.json` 是核心规格的一部分
- ✅ `character.json` 只是上层扩展规范中定义的一个模块示例

类比：HTTP 不定义 HTML，ZIP 不定义文件内容格式。

### 补充规范 13：数据结构应完全由 manifest 驱动

包内不应该有"默认必须存在"的文件。有什么数据块、在什么路径、是什么类型——全部由 manifest 的 entries 声明。

- ❌ "包必须包含 character.json"
- ✅ "manifest 声明了哪些数据块，包就包含哪些数据块"

### 补充规范 14：区分协议层与扩展层

```
协议层（PersonaSeed）:
    容器格式、manifest、模块注册、校验、迁移
    → 完全通用，不知道任何业务概念

扩展层（Eidolon 生态）:
    character-schema、personality-format、memory-schema
    → 建立在协议之上的具体数据模块规范
```

文档结构中应有明确的分隔——核心协议规格 vs 扩展模块规格应放在不同目录或明确标注。

### 补充规范 15：入口数据应为通用结构

API 返回的数据结构应反映协议的通用性。`Package` 的核心字段应该是：

- `manifest` — 元信息
- `entries` — 数据块字典（key 为 entry id，value 为原始字节 + 类型标签）
- 不应有 `characters`、`personality` 等业务字段

消费方根据每个 entry 的 `type` 自行路由到解析器。

### 补充规范 16：检查抽象层级

编写任何文档后，用这个问题自检：

> 如果这个协议明天被用来打包一个游戏 NPC 或虚拟宠物，有哪些内容需要修改？

如果需要修改的只是"把 character 改成 npc"，说明抽象层级正确。
如果需要修改协议核心结构，说明抽象层级不对——协议知道了不该知道的东西。

## 第四轮补充：冻结边界与实现优先

经过最终修订轮次，协议层冻结。以下是从冻结过程中总结的最后几条规范。

### 补充规范 17：区分 Data 与 Resource 的生命周期

数据块（Data）和资源文件（Resource）有不同的生命周期，不应混在一起管理。

```
Data（数据块）:                    Resource（资源）:
├── 实体定义数据                    ├── 媒体资产
├── 随实体版本变化                  ├── 可独立于实体版本更新
├── 通常较小（KB 级）               ├── 可能很大（MB-GB 级）
└── 修改实体设定时更新              └── 替换美术资源时更新
```

- ❌ 资源和数据混在同一个目录结构中，修改角色描述时被迫重新处理几百 MB 的资源
- ✅ 包内 `data/` 和 `resources/` 分离，manifest 中也分别声明（`entries` vs `resources`）

### 补充规范 18：保留最小身份，但不定义人格

任何实体协议都需要最小身份标识，但这是**实体识别**，不是**角色定义**。

- ✅ `id` (UUID) + `name` (显示名称) —— 实体识别的最小集合
- ❌ `personality`、`background`、`appearance` —— 这些是扩展模块的内容

类比：Docker image ID + tag、Git commit hash、文件 inode。这些都是实体识别，不定义实体内容。

### 补充规范 19：使用 MIME 风格的类型标签

协议中的 `type` 字段应采用 MIME 风格，以兼容现有工具生态。

- ✅ `"application/json"`、`"image/png"`、`"application/x-eidolon-personality"`
- ❌ `"json"`、`"image"`、`"personality"`

`application/x-*` 前缀用于自定义类型。

### 补充规范 20：判断抽象层级的上下边界

继续抽象有两个方向，都不可取：

```
往下（过底）：                     往上（过高）：
文件系统级别                        人格标准级别
├── 数据块如何存储                  ├── 什么叫人格
├── 二进制序列化协议                ├── 什么叫记忆
├── 分布式同步                      ├── 什么叫意识
└── 数据查询语言                    └── 什么叫角色
    ↑                                  ↑
    ZIP/SQLite/Git/IPFS 的职责        尚无稳定答案
```

协议应站在基础设施之上、业务标准之下。如果继续往下，你在重新发明 ZIP。如果继续往上，你在冻结一个不存在的心理模型。

### 补充规范 21：当最大风险从"设计不足"变为"设计过度"时，停止设计

设计过程中存在一个转折点：继续设计的边际收益趋近于零，而通过实际实现暴露缺陷的收益开始超过纸面预测。

判断这个转折点的信号：
- 用户开始说"继续抽象的收益已经很低"、"现在不应继续设计"
- 讨论的重点从"还需要定义什么"变为"已经定义的东西是否过多"
- 协议可以用一句话自证：如果明天用它打包一个完全不同的实体类型，协议核心结构不需要修改

> **"稳定的部分进入核心，不稳定的部分成为扩展。"**
> 当一个数据协议覆盖了容器、清单、模块、资源、版本这五个维度，它就已经具备了长期可扩展的基础。继续设计的收益递减。

### 补充规范 22：开发顺序不可逆

```
协议规范 → 参考实现 → 编辑工具 → 运行时 → 上层系统
```

不要因为在文档中看到了未来的可能性，就跳过当前阶段去实现后面的东西。

- ❌ 在协议冻结前开始写 Runtime 代码
- ❌ 在 toolkit 完成前开始做 GUI 编辑器
- ✅ 每个阶段完成后，下一阶段的需求会更清晰，部分设计甚至会被推翻

### 补充规范 23：模块入口必须声明 `required` 字段

`entries` 中的每个数据块必须声明 `required: true/false`：

- `required: true` → 缺失视为包损坏
- `required: false` → 缺失则消费方静默跳过

这允许协议在不理解模块内容的情况下做出兼容性判断。
