# 文档编写规范

> 本文档规定 Eidolon 生态下文档的编写原则——文档应该讲述什么、不该讲述什么。
> 相关规范：[设计文档编写规范](./design-document-conventions.md)（边界优先、不做临时方案等原则同样适用）

## 1. 核心原则：文档不是代码的翻译

代码已经说清楚了"怎么做"。文档的价值在于说清楚**"为什么这样做"**和**"整体是什么"**。

一份好的设计文档，读者看完后应该能理解：
- 这个系统的核心命题是什么
- 为什么选择这种架构而非其他
- 各部分的职责边界在哪
- 它们之间如何协作

一份坏的文档，读者看完后只得到：
- 有哪些文件
- 有哪些函数
- 路径是什么
- ——这些信息应该从代码中获取，不需要文档复述。

## 2. 文档不应包含的内容

以下信息属于"代码的副本"，不应出现在设计文档中：

| 不应出现 | 理由 | 正确的做法 |
|---------|------|-----------|
| 具体文件路径（`format/Cartridge/cartridge/api.py`） | 路径会随重构改变，文档跟不上 | 用逻辑概念替代——"协议层的容器模块" |
| 函数/类签名（`build_package(character, images)`） | 签名的权威来源是代码，文档不应成为第二份 | 描述能力——"提供组装能力，将领域对象和资源源文件粘成标准包" |
| 包名和安装命令（`pip install cartridge`） | 属于操作手册/README，不属于设计文档 | 只说明依赖方向——"协议层 ← 资产类型层" |
| API 名称列表（`open()` / `write()` / `validate()`） | 代码即文档，API 文档是另一类文档 | 描述核心能力——"容器打开、序列化、校验" |
| 具体项目名作为设计概念（PersonaSeed、eidolon-character） | 项目名会变（PersonaSeed→Cartridge），设计原理不应变 | 用层名称——"协议层"、"资产类型层"、"运行时" |

## 3. 文档应该包含的内容

### 3.1 核心命题

每份文档开头应有一句话讲清楚这份文档要回答什么问题。

```
好："稳定的部分进入核心，不稳定的部分成为扩展。"
坏："Eidolon 采用多独立项目架构，包含以下仓库：..."
```

### 3.2 设计原理

讲清楚**为什么**这样设计，而不是**设计了什么**。

```
好："data 与 resource 分离的理由是二者有不同的生命周期——
      修改角色设定不应触发几百 MB 资源的重新处理。"
坏："data/ 目录存放结构化数据，resources/ 目录存放二进制文件。"
```

### 3.3 边界与契约

层与层之间的交互契约——谁负责什么、不负责什么、用什么方式协作。

```
好："协议层提供通用容器视图，不预判哪些资产类型合法；
      消费方按类型标签自行路由——协议层不认识它，但能路由它。"
坏："运行时调用 cartridge.open() 获取 Package，遍历 entries 按 type 派发。"
```

### 3.4 概念模型

用类比建立心智模型，而不是罗列实现细节。

```
好：游戏引擎类比——".unity 文件格式 : Unity :: 协议层 : Eidolon"
坏："PersonaSeed 是 Eidolon 引擎的项目文件格式，类似 Unity 的 .unity 文件。"
```

### 3.5 约束与决策

已经做出的设计决策及其理由，被推翻的方案及推翻理由。

## 4. 命名规范

文档中使用**层名称**而非具体项目名称：

| 使用 | 而非 |
|------|------|
| 协议层 | Cartridge / PersonaSeed |
| 资产类型层 | eidolon-character |
| 引擎运行时 | eidolon-runtime |
| 编辑器层 | eidolon-studio |
| 标准包 | `.cart` / `.seed` |

例外：需要区分同层中不同项目时（如"角色资产"vs"人格资产"），可用功能性名称（"角色资产类型""人格资产类型"）。

## 5. 文档分层

文档应放在正确的层级：

| 内容 | 归属 |
|------|------|
| 生态架构、跨层协议、仓库管理 | 顶层 `docs/` |
| 某个子项目的格式规范、API 文档 | 子项目 `docs/` |
| Agent 工作规范（如本文件） | `agent-conventions/` |

**子项目中不应存在顶层文档的副本。** 每份文档只有一个权威来源。

## 6. 审查检查清单

编写或修改文档后，逐条检查：

1. [ ] 有没有文件路径？——去掉，用逻辑概念替代
2. [ ] 有没有函数/类名？——去掉，描述能力
3. [ ] 有没有包名或安装命令？——去掉或移到操作手册
4. [ ] 第一段有没有说清楚"这份文档回答什么问题"？
5. [ ] 设计决策有没有解释"为什么"而不只是"是什么"？
6. [ ] 有没有用具体项目名（PersonaSeed、Cartridge）代替层名称（协议层）？
7. [ ] 这份文档的权威来源是否唯一？（不存在多份副本）
8. [ ] 如果明天项目改名或重构，这份文档有多少内容需要修改？——越少越好
